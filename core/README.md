# Core

## Purpose

The shared services every other area stands on: the event bus, the content registry, input, per-player UI focus, saving, base classes, the projectile manager and object pools. Gameplay, HUD and content build on it; it builds on nothing of theirs.

## Contract

- **Dependency direction:** `core` ← `gameplay` ← `content`. `core/` depends on none of `gameplay/`, `hud/` or `content/`. It finds content by folder through `core/registry`.
- **Sub-folders, one per service:**
  - `events/`: the event bus (`spell_cast`, `enemy_died`, `player_downed`, `room_cleared`, ...). One autoload, `Events` (`events/events.gd`), with a typed signal per event: caster-keyed events name the actor id first (`caster`), seat-keyed ones the seat (`player`), actors G3b. Areas talk only through it. **Commands** (online-ready N2): the HUD's requests the simulation hears (`InputFrame.COMMAND_NAMES`: the builder's, the horde's picks, the sandbox page's, rewards, doors) apply at the next tick's start, never mid-tick: the bus hands each to `command_sink` (the `Frames` autoload, `sim/`), which puts it into its seat's next input frame and applies it then (`apply_command`); the HUD sends them as before, and the simulation hears them through `listen(name, callable)`, never by connecting to the signal. With no sink (a test's own bus) a command applies as it is sent. A new HUD request the simulation hears goes into `InputFrame.COMMAND_NAMES` with its shape, and its listener uses `listen`. It owns the event definitions; each area's README lists only which events the area sends and listens to.
  - `registry/`: discovers content by folder, so no central list is edited. One autoload, `Registry` (`registry/registry.gd`), scans `content/` and `audio/` when the game starts (`scan()` again with other roots, for tests). `get_resource(folder, id)`, `get_ids(folder)`, `get_all(folder)` and `get_folders()` answer by folder (`spells`, `enemies`, `rooms`, ... the direct children of `content/`) and id; every `.tres` below a folder that has an `id` is registered, at any depth, and the first file in sorted path order wins a duplicate id (with a warning). Every build sees every resource: there is no demo subset (owner, 2026-11-05). `validate_spells()` runs the spell validator on everything under `spells` and the reaction table (and in a debug build the registry pushes a warning per problem at start). `get_sound(id)` returns the `.ogg` under `audio/` whose file name is the id, or `null` when there is none; gameplay and feel ask for a sound by id and play nothing on `null`, so a missing sound is silent and never an error. It is the only script that loads from a computed path; everyone else uses literal `load("res://...")` or `preload(...)`.
  - `input/`: one autoload, `PlayerInput` (`input/input_manager.gd`); devices join with a button press and each player gets their own device. A gamepad takes the lowest free index; the keyboard and mouse only take P1 (index 0), so P2–P4 are gamepads. The `leave` action or an unplugged gamepad frees the slot. Bots join with a virtual device per index (`add_virtual_device`; `send_virtual` for a menu's buttons, through the same `handle_event` path as real input) and fill their seat's input frames (`sim/`, `Frames.set_source`). **The simulation never reads a device** (online-ready N2): `local_input.gd` (`LocalInput`) is the local input layer in front of a seat's input frame (the walk, the stick's aim hold, the mouse turned into a direction from the hand, the staff buttons' press counts, captured), kept per seat by the `Frames` autoload. Menus, the HUD and UI focus ask by player index (`get_move`, `is_action_pressed`, `is_action_just_pressed`) and never reads `Input` itself (call `is_action_just_pressed` only from `_process` or `_physics_process`). Each physical input is tracked on its own and an action takes the strongest, so releasing one of two held inputs does not cancel the other. The actions (`move_left`, `move_right`, `move_up`, `move_down`; the four staffs `staff_1` to `staff_4` on RB, RT, LB, LT, or Space, the left and right mouse buttons and Q; the menus' `accept` (A), `back` (B, which opens the builder in play) and `alternate` (X); `pause` (Start or Escape); `page_prev` and `page_next` (LB, RB); `extra` (Y; R), a menu's third action; `kind_prev` and `kind_next` (the d-pad's left and right only; Page Up, Page Down); `join`, `leave`) are in `project.godot`; the triggers are axes, so the manager routes them itself. Aim: `get_aim(player)` is the right stick as a unit vector (zero in the dead zone; `send_virtual_aim` for bots) and `is_mouse_aiming(player)` is a flag for the keyboard player (a mouse move or click sets it, the keyboard `staff_2` key, J, clears it); the local input layer (`LocalInput`) turns the mouse into a direction from the hand of the actor the seat drives, because that needs the world. `PlayerInput` sends `device_joined` and `device_left`; `coop` turns them into `player_joined` and `player_left`. `set_captured(player, true)` hides a player's move and the four staff actions from those gameplay questions (the menu actions stay) while their UI panel is open, so gameplay needs no check of its own; `get_press_count` counts presses and is never captured, so UI code loses no quick tap. A menu that steers with the sticks (the radial builder) reads `menu_move(player)` (the left stick alone on a pad, the move keys or virtual move actions otherwise) and `menu_aim(player)` (the right stick), which answer while captured; `menu_tilt(player)` is the right stick with how far it is pushed (0 to 1 past the dead zone), for the radial's zoom and kind rings. `is_held(player, action)` says whether a button is down captured or not, for the menu that holds the capture (the radial's LT held clears). `rumble(player, weak, strong, seconds)` shakes a player's pad (never the keyboard) through `vibrator`, which tests replace. **Glyphs:** `glyph_kind(player)` says what a player holds (`input_glyphs.gd`, `Kind`: keyboard, keyboard with the mouse aiming, Xbox, PlayStation, Switch or a plain gamepad, told apart by `Input.get_joy_name` when the device joins, by brand word or by the vendor id a browser puts in the name) and `glyph_kind_changed(player)` fires when it changes (a join, a leave, the mouse aim turning on or off). `InputGlyphs.glyph(kind, action)` gives the button to draw for an action (shape, label, colour); the HUD draws it (`hud/widgets/action_glyph.gd`). A player's device only changes by leave and join, so that is when pad type changes. A keyboard joined only by a mouse click on Play holds P1 provisionally: the first gamepad to press join takes P1 over until the keyboard is used (owner 2026-10-27).
  - `actors/`: the actor table, one autoload, `Actors` (`actors/actors.gd`; actors G2, docs/milestones/M2-actors.md). An actor is anything that acts (a player, an enemy), and its id (0–1023, `ACTORS`) is its row in every system. `open(team, ramp, seat)` hands out the lowest free id (`NONE`, -1, when full), `close(id)` frees it; `is_open`, `team_of` (`TEAM_WIZARDS`, `TEAM_ENEMIES`: for aim only), `ramp_of` (0–3 the hat colours, `RAMP_ENEMY`), `seat_of` (0–3 or `NONE`); `set_driver(id, team, seat)` is a controller change, and a seat drives one actor at a time (the newer takes it, the older is left unseated); `actor_of_seat(seat)`; `set_home(id, seat)` and `home_of_seat(seat)` (a seat's own body, kept while it drives another actor); `budget_of(id)` is the seat while a seat drives it, else `SHARED` (4); `set_node`/`node_of` keep only an instance id (null once freed); `clear()`. Bad ids answer `NONE` and change nothing. Packed arrays, nothing allocated after start. The bodies open their own ids (players, enemies that cast, the actor kit), and every system keys its arrays by them (G3). See `actors/README.md`.
  - `sim/`: the simulation's own tools and its one input path (online-ready, phase N). **Input (N2):** `InputFrame` (one seat's input for one tick: the move and aim quantised, the staff buttons, captured, the tick's commands; strict bytes), the `Frames` autoload (`frames.gd`: at each tick's start (the Tick calls `tick` first, `sim/tick.gd`), each seat's frame from a replay, a `FrameSource` such as a bot, or its device through `LocalInput`; the commands applied; `record` and `play`), `Replay` (a run's start, seed, content and frames; `user://replays/` only). A `PlayerController` builds its intent from `Frames.frame_of(seat)`. **The state:** `StateWalk` (every member of a simulation script is state unless listed in `DERIVED` or `VIEW`; references to other bodies in `REFS` are state, walked as who they point at), `SimHash` (a hash per area), `Desync` (the first tick two runs part, and the members that differ) and `SimSeed` (`SimSeed.fresh()`: the one seed nobody chose; simulation code calls no `randomize()`, global dice or clock, a test reads their source). Tests and tools only, never a normal tick, except `SimSeed`. Its README lists the simulation folders.
  - `ui_focus/`: per-player UI focus, because Godot has one global focus. One autoload, `UIFocus` (`ui_focus/ui_focus.gd`). `open(player, controls)` gives a player a panel; only that player's input (through `PlayerInput`) moves it: up/left and down/right step through the controls, `accept` (A) activates, `back` (B) cancels, `alternate` (X) sends `alternate` for the focused control and `page_prev` / `page_next` (LB, RB) send `paged` (presses come from `get_press_count`, so a quick tap is not lost). A panel laid out in two dimensions gives `set_navigator(player, callable)`: each move asks it for the control in that direction first (kept when the panel is opened again with new controls, cleared when it closes); `focus(player, control)` jumps to a control. An open panel captures its owner's gameplay input through `PlayerInput.set_captured`, so their staff does not walk or cast meanwhile; opening needs a joined device. A focused control that gets disabled, hidden or freed loses focus and is never activated. It has its own signals (`opened`, `closed`, `focus_changed`, `activated`, `cancelled`, `alternate`, `paged`, player index first); a widget checks that the player is its owner. It never calls `grab_focus`, never pauses, and closes a panel when its player's device leaves. Every widget builds on it.
  - `settings/`: the numbers of player settings that more than one area reads, so neither reads the other: `EffectSlots` (`settings/effect_slots.gd`; owner 2026-10-27), the range, step and default of the pause menu's "Effect slots" slider and feel's effect batch, and `snap`; `ShotCap` (`settings/shot_cap.gd`; owner 2026-11-02), the stops of the "Max shots" slider, the platform's cap (`default_cap()`, the projectile manager's `DEFAULT_CAP_WEB` or `DEFAULT_CAP_DESKTOP`) and `snap`; the menu sends `projectile_cap_changed`, which `Projectiles` applies with `set_cap`; `MoteCap` (`settings/mote_cap.gd`; spell spectacle P1a), the stops of the "Particles" slider (Off, Low, Medium, High: how many motes Feel's ring holds), the platform's cap (`default_cap()`: 8,192 on the web, 32,768 on desktop), `snap` and `word_of`; the menu sends `mote_cap_changed`, which Feel applies with `set_mote_cap`; `MoteDensity` (`settings/mote_density.gd`; P1b), the stops of the "Particle amount" slider (None, Half, Full, Double: the share of its count every burst of motes throws), its default, `snap` and `word_of`; the menu sends `mote_density_changed`, which Feel applies with `set_mote_density`; `FloorMarks` (`settings/floor_marks.gd`; spell spectacle P2a), the "Floor marks" switch's platform default (`default_on()`, on for both until P2 measures the web); the menu sends `floor_marks_changed`, which Feel applies with `set_floor_marks`; `TaillessMotes` (`settings/tailless_motes.gd`; S5 step 4, a dev setting), the stops of the "Tailless motes" slider (2048, 4096, 8192: the births' pool with the tails off) and `frame_rows_of`, the motes' rows a frame for a pool; the menu sends `tailless_motes_changed`, which the projectile manager applies with `set_tailless_pool` and feel with `Motes.frame_rows`. The stepped ones (`ShotCap`, `MoteCap`, `MoteDensity`) find their nearest stop with one helper, `SettingStops.nearest` (`settings/setting_stops.gd`; spell spectacle 2, S1), so a new stepped setting is its stops, its words and one line. (`EnemyFire`, the Enemy fire switch's default, went with the switch in actors G3c.)
  - `loading/`: the loading screen's service, one autoload, `Loading` (`loading/loading.gd`, last in the autoload list; owner 2026-10-29: the work before playing happens behind a loading screen, not on the menu or in the room). `run(tasks, done)` does a list of LoadTasks one unit a frame (after `WAIT_FRAMES`, so the screen is drawn first), sends `loading_started`, `loading_progressed(done, total)` and `loading_finished` (the HUD's screen, `hud/panels/loading/`, is drawn from those alone), then calls `done`; `cancel()` drops it without `done`; one load at a time (`is_loading`, `progress`). A LoadTask (`loading/load_task.gd`) is a RefCounted with `units`, `units_done`, `begin(host)`, `step` (one unit), `is_done`, `end`; the shader warm-up is one (`projectiles/shader_warmup.gd`). **Starting to play:** Flow asks `Flow.play_tasks()` for what must be ready before a room and runs it here on Play and Sandbox; to load something more before playing (a room's art, a generated level), write a LoadTask and add it there.
  - `display/`: the game window, one autoload, `Display` (`display/display.gd`; owner 2026-10-27). The `fullscreen` action (F11, Alt+Enter) and `toggle_fullscreen()` switch fullscreen on and off anywhere; `is_fullscreen()` reads the window itself. The main menu and the pause menu's Settings page have a switch. On the web the browser allows it only after a key press or click, not a gamepad button.
  - `save/`: reading and writing under `user://` only. `save_file.gd` (`SaveFile`, living staffs H6): one ConfigFile (`user://save.cfg`) of flags, `has_flag`/`set_flag` (written at once), `is_new`, and settings (`get_setting(key, fallback)`, `set_setting(key, value)`, also written at once; the screen shake switch uses one); a missing or broken file is a new save. Runs and unlocks join it in M3.
  - `base/`: base classes (`enemy_base.gd`, `room_base.gd`: small M1 resources with an `id`; a room's `ambient` is its light where nothing lights it, for spell light, 1.0 by default) and build info. **Light spots (spell spectacle P3b):** `LightSpot` (`light_spot.gd`) reads a light that is part of a room's art from a plain node in the group `light_spot` (rooms carry no scripts), its numbers as metadata (`light_reach`, `light_strength`, `light_flicker`, `light_art`, `light_tint`), its colour its art's; `problems` for the content tests. **Flash kinds (docs/milestones/flash-kinds.md):** `FlashKind` (`flash_kind.gd`, files in `content/flashes/`): a kind of Feel's flashes, how it is drawn (`draw`: a `shape` from its curves, which the flash shader reads from a table, or a drawing of code: the poof's clouds, the cracks, an explosion's parts, lightning), its seconds, step and room light, and its curves over its life (a cross, a dotted disc, a ring, a column, its glow, its two shades); `problems` for the content tests. **Mote kinds (spell spectacle P1a):** `MoteKind` (`mote_kind.gd`, files in `content/motes/`): how a kind of Feel's motes flies (gravity, drag, bounce, sway, glow, first shade), what it looks like (`shape`: a multi-line text picture of up to 5x5 pixels, one row a line, frames apart by a blank line, `#` its shade, `o` the shade hotter, `.` none; `shape_frames()`; `shape_play` life, loop or pick; `shape_rate`; `shape_turns` with its flight; `shape_pixels(frame)`) and how a burst throws it (count, speed, spread, up, life, height), the cards it is the motes of by id (`cards`; spell spectacle 2, S2: a card's kinds are those naming it, else its look layer's) or by look layer (`look_layers`; 0 for a shot with none), or `surface` (what a struck wall sheds; a room may name its own, `RoomBase.surface_kinds`), or none (thrown only where a cue or a room names it), and `problems()`; it holds no colour. **Floor mark kinds (spell spectacle P2a):** `MarkKind` (`mark_kind.gd`, files in `content/marks/`): a mark a cue's `mark` part stamps into Feel's floor mark layer (`CueBase` documents the part's keys, `MARK_KEYS`): its `form` (blot, crack, rime) and numbers (`rough`, `fill`, `lines`) that the mark shader draws it from, where its body's and its edge's colours come from (`floor` or `spell`) and which shade (`base` or `shadow`, STYLE.md), and the cards it is the mark of by id (`cards`) or by look layer (`look_layers`), for a part with `cards`; `problems()`. **A room's floor:** its layout's `Floor` sprite is at `RoomBase.FLOOR_Z` (-2), under the marks; `RoomBase.floor_colors()` (light, base, shadow) is `floor_mark_colors` when set, else sampled once from the `Floor` sprite's art times its modulate (colours on at least `FLOOR_MIN_SHARE` of the most common's pixels). **A room's surface colours:** `RoomBase.surface_colors()` is what its walls shed (light, base, shadow): `debris_colors` when set, else sampled once from its scene's art (the colours of the sprites on its wall bodies, most common first, leaving out the `Floor` sprite's most common colour, so debris shows on the floor). **Enemy data (enemy AI AI4, docs/milestones/M2-enemy-ai.md):** `EnemyBase` holds `staffs` (1–4 `StaffCards`, `staff_cards.gd`: a `StaffBase` and its `cards`), a `profile` (`AIProfile`, `ai_profile.gd`: aggression, caution, accuracy, lead, reaction, dodge, windup and rest scales, track speed, channel time, commitment, randomness, teamwork; `AIProfile.fallback()` for none; no `id`, so the registry never lists one), `phases` (`EnemyPhase`, `enemy_phase.gd`: `health_below` or `after_seconds`, its staffs, profile, `PhaseLook` (`phase_look.gd`: texture, face style, glow, size) and `transition`) and `size`; `problems()` names what is wrong (more cards than slots, more than 4 staffs, a phase with no condition), `has_staffs()`, `profile_or_fallback()`. M2's spell components (part 1) are `spell_component.gd` (`SpellComponent`: `id`, `display_name`, `complexity` 1–4, `icon`, `kind()`, `ranges()` and `range_problems()`) and its four kinds `form_base.gd` (`FormBase`), `element_base.gd` (`ElementBase`), `modifier_base.gd` (`ModifierBase`) and `trigger_base.gd` (`TriggerBase`), each documenting its fields and allowed ranges; the element reactions are `reaction_table.gd` (`ReactionTable`, `find(status_id, element_id)`) of `reaction_row.gd` rows (`content/spells/reactions.tres` holds six reactions as twelve rows, one per direction), which have no `id`, so the registry never takes them for content. M1's `SpellBase` is gone (M2 part 11): the one way to fire is `Spells.cast_staff(player, staff, origin, direction, mana)`, which returns the mana spent or `REFUSED`. Players and bots call it and read no spell field; `tests/core/test_spell_field_reads.gd` fails when a script outside `content/spells/`, `core/base/` and `core/spells/` does. **Staffs rework (A3, docs/milestones/M2-staffs.md):** a fifth card kind, `multicast_base.gd` (`MulticastBase`: `extra_draws`, `mode` TOGETHER, SCATTER or BURST, `repeats`, `repeat_interval`, `mana_cost`, `wind_down`); the carrier a form fires, by name (`FormBase.carrier`: &"atom" to &"slam", each a script in `spells/carriers/`; `carries_payload()` for a rain), modifier behaviours (SHIELD to RELAY, `behaviour_strength` up to 256) and trigger events (BLOCK to ALLY), each commented with the kit that runs it; and `staff_base.gd` (`StaffBase`: `id`, `display_name`, `slots`, `draw`, `wind_up`, `cooldown`, `spread`, `ranges()`, `range_problems()`), which is not a card: staffs live in `content/wizard/staffs/`. `build_info.gd` holds the build info.
  - `story/`: `story_validator.gd` (`StoryValidator`, M2 part 23) holds the rules of a line players read (`check_line`: one line, at most `MAX_LORE_CHARS`; `format`) and returns problems like `SpellValidator`. The cards' descriptions are a field of the card (`SpellComponent.description`, since 2026-11-05): `Spells.component_description(id)` gives the text, `SpellValidator.check_descriptions` checks them, `Registry.validate_story()` runs it over every card (a missing one only warns) and `warn_story_problems()` pushes them in a debug build.
  - `spells/` (staffs A4; the staff codes of D2 are gone, owner 2026-10-31): `Spells.compile_staff(cards, staff)` reads a staff's cards into a `CompiledStaff` (`compiled_staff.gd`: the `casts` of one cycle, every compiled spell in `nodes`, and the `wasted` cards, slot -> true) with `staff_compiler.gd` (`StaffCompiler`, the reading rules of docs/milestones/M2-staffs.md); each `CompiledCast` (`compiled_cast.gd`) has its `group` (`CompiledGroup`: `spells`, `scatter`, `repeats`), the slots it read, `mana`, `wind_down`, `delay` (the wind-down, plus the staff's cooldown when it ends the cycle), `ends_cycle`, `wrapped`, `targets` (what each card attached to) and a plain `description`. **Wasted triggers (rules R2b):** a trigger whose event never happens on its carrier is listed in `wasted` (`Carrier.fires_with`, from what each trigger needs in `TriggerBase.NEEDS`: on hit, on kill and on reaction on carriers that hit (a decoy or familiar only with a blast, whose hits are its hits), timer and on hurt on every carrier that lasts, not on a slam or teleport, which are over at once (rules R4d), on wall only on flying shots and beams, on block wherever a shield or deflect runs, so not on a rain or familiar), as is one missing the card its event needs (on block a shield or deflect, on reaction an infusion or relay, on kill and on reaction on a carrier that hits nothing itself a blast, on wall no ghost on a flying shot). Its payload is still read, so the cards after it read in the same order, but it is not attached: each of its cards is wasted ("Nothing casts it") and costs no mana or time. A compiled spell now also has `fallback` (on the caster or on a payload's origin), `element_ids`, `behaviours` (summed strength per `ModifierBase.Behaviour`), `triggers` (each trigger with its own payload, in slot order; `payload` is the first one's), `own_payload`, `node` and `slot`. **Spell names (E1)** are gone (owner, 2026-10-31): a cast is called by its plain `description`. `Spells.staff_view(cards, staff)` gives the builder plain values (each cast's `slots`, `text`, numbers, `targets`, `wasted` and its `tree`: the rows the builder's tree draws, depth first, each `depth`, `trigger` slot or -1, `slots` and `name`, the first with the cast's `mana` and `damage`, from `Spells.cast_tree`, which reads each compiled spell's own `card_slots` and each group's `multicast_slots`; and hands `staff` back, so a builder can preview other cards in the same staff). **The staff runtime (A5):** `spells.gd` (the `Spells` autoload, class `SpellRuntime`) casts. **Carriers** (`carriers/`, docs/CARRIERS.md): each carrier is a `Carrier` script known by its name (`CarrierAtom`, `CarrierBeam`, ... found by `Carriers.of(&"beam")`, the `carrier` a form card names) that answers yes/no questions about itself (`traits()`: does it fly, hit, last, move its caster...); each card says what it needs from a carrier (`ModifierBase.NEEDS`, `TriggerBase.NEEDS`), and which cards do nothing on a carrier, with the builder's sentence, is worked out from the two (`tests/core/test_card_rules.gd` checks it by playing every card on every carrier); the compiler asks them, and the runtime makes its own bound set (`Carriers.make_all`) and hands each launch to its carrier (`launch`, `shoot`, `on_hit`, `on_move_end`, `step`, ...), so `spells.gd` never asks which carrier a spell has and names none. A carrier asks the runtime for the rest only through `carrier_kit.gd` (`CarrierKit`: the cast under way, the aim, the shot kit, the hit path, payloads, live carriers, moves, entities), never through `Spells`' own members. The beam, swing and slam carriers keep rows of their own; `staff_poses.gd` (`StaffPoses`) plays the staff animations. Every hit with no shot slot (a beam's, a sweep's, a strike's, a zap, a jump) goes back through `Spells` as one `RayHit` (`ray_hit.gd`), so cards, payloads and chains have one path; the looks read the carriers' rows from `Spells.carrier(id)` (typed: `CarrierBeam.of(spells)`, `CarrierSwing`, `CarrierSlam`, and `CarrierDash`, `CarrierDecoy` for the body and `ai`) and the staff animations from `poses()`. `install_staff(player, staff, compiled)` makes a compiled staff the build of one of a player's four staffs (a new generation; editing switches its sustained carriers off) and `cast_staff(player, staff, origin, direction, mana)` fires the next cast of its cycle, returns the mana spent or `REFUSED`, and moves the cursor (`cast_index`) and the delay (`cooldown_left`: the cast's wind-down, and the staff's `cooldown` after the cycle's last cast; a sustained carrier's switch-off press frees the staff at once). **Wind-up (cast-timing T2):** a cast whose `wind_up` (its staff's, plus every carrier's of its own group and their modifiers' `wind_up_add`) is above 0 does not leave at the press: `cast_staff` returns 0.0, the staff is busy for the wind-up (`is_winding`, `cooldown_left`), its pose winds turning with the live aim (`_wind_pose`, the carrier's `pose_side`), and when it is over the cast leaves from where the caster holds the staff along its aim then (`set_aim`), its mana paid then (`mana_spend_requested`, which every Caster hears); being downed (`clear_aim`), a rebuild or a closed caster cancels it, and nothing is paid. A payload group whose `wind_up` is above 0 waits that long where its trigger fired, then fires as it would have (`_fire`, `PendingLaunch.wound`). **Skipping (cast-timing T3):** a cast its staff's mana does not pay is skipped: the press fires the first cast after it that the mana pays, up to the cycle's end (`_firing_cast`); with none, the cycle ends there, its cooldown runs, nothing is paid and `cast_fizzled` is sent. `cast_ready` and `next_cast_mana`, `next_cast_sense`, `next_cast_reach` and `next_cast_radius` (given the mana; the Caster passes its free mana) read the cast a press would fire. Tags (`SpellTag`, one caster field since actors G2) are staff (bits 0–1), generation (2–4), node (5–13: the compiled spell's index, up to 511) and caster (14–23: 0–1023, every actor id) under `FLAG` (bit 24), clear of the enemy attack tags and below `SpellTag.LIMIT` (`1 << 29`): `make(caster, staff, node, generation)`, `caster_of`.     - **The step, by behaviour (2026-10-28):** `step` runs in passes: a common pass (life, and a straight shot flies on along its velocity), then one pass per behaviour over the list of only the shots that have it (stuck, growth, linger, orbit, return, homing, spiral, a card's move; their order and why is the comment above `B_STUCK`), then the hit pass, which takes every shot in turn as the step always did (ends marked by the passes, bounds, walls, hits, events), then the passes after the hits (shield: it looks only at the shots on the grid cells its path could touch, and is not charged to the hit-work budget, so a block always happens; rules R4a). A kernel reads the manager's packed arrays for one call and writes them in place, so nothing may keep a copy of them expecting it to stay; a kernel never grows an array, so the manager sizes them first. Changing a hot loop means changing its kernel too ([native/README.md](../native/README.md)). Its loops over every shot run on several threads (shot scale H5, native/README.md "Threads"; the hit pass stays on one); `native_threads` sets how many (0: the kernel's own choice), and the bits are the same on any number. Measured (2026-11-02, 3,000 shots, in WASM): a step with no targets 8.4 → 0.66 ms, homing 17.9 → 1.0 ms, orbit 11.8 → 1.9 ms, `update_draw` 20.1 → 1.1 ms; the desktop stress frame 116 → 69 ms.
  - `pools/`: object pools; no per-frame allocations. `pools/pool.gd` is a fixed-size pool typed by its factory Callable: it makes every object up front, `acquire()` returns an object or `null` when all are out (it never grows), `release()` takes one back (a double or foreign release is refused), and optional `on_acquire` and `on_release` hooks reset state. `clear()` frees every object, including ones still handed out, so drop your references first. Pools are for nodes and effects (enemies, damage numbers); projectiles are packed-array rows and do not use them. Use `preload("res://core/pools/pool.gd")`.
- Most services arrive in M1 (docs/ROADMAP.md). Folders without code yet only hold a `.gitkeep`; so far `actors/`, `base/`, `native/`, `display/`, `events/`, `input/`, `pools/`, `projectiles/`, `registry/`, `spells/` and `ui_focus/` have code. Each service gets its entry script and a section here when it is built.
- Services that act per caster take an actor id (`core/actors`); only the HUD's, input's and co-op's take a seat 0–3. Nothing assumes a single player.
