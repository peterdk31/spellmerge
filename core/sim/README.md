# Sim

## Purpose

The simulation's own tools (online-ready, phase N, [docs/milestones/online-ready.md](../../docs/milestones/online-ready.md)): the same inputs must give the same game, to the bit, on every machine, so online co-op can send inputs only. N1 brings the state walker, the state hash, the desync report and the one source of a seed nobody chose; N2 the one input path (input frames, the frames service, replays); N3a the one clock (the Tick); N3b a run's start from a fresh game's state; N3c the `sim` service (time and chance by hash); N10 snapshots (the whole game saved and made again: a player joining a run, a replay sought, rollback later).

## The simulation folders

Every script in these folders, and every inner class of one, is a **simulation script** (`StateWalk.FOLDERS`): simulation by default, so a new gameplay folder is covered the day it gets its first script (N9).

| Folder | Why |
|---|---|
| `core/actors/` | the actor table: who an actor is |
| `core/items/` | the item stacks an inventory holds (items I3) |
| `core/projectiles/` | every shot, its hits and its trails' samples |
| `core/spells/` | the spell runtime, staffs, carriers |
| `gameplay/` | every gameplay area (actor, ai, combat, coop, flow, player, and any new one), but `gameplay/feel/` |

`gameplay/feel/` is view as a whole (`StateWalk.VIEW_FOLDERS`): it draws the game, plays its sounds and drives the party's camera, and only reads the game. `core/sim/` is not a simulation folder: these tools read the simulation and feed it its input, they are not part of it. Everything else (Feel, the HUD, the camera, looks) is view: it may use real time and its own generators, as long as it only reads the game.

## The line (N9)

Simulation code runs on the tick, the same on every machine. `tests/core/test_sim_rules.gd` reads every simulation script against one table (`RULES`: what a line does, and the fix) and fails on:

- **the clock** in any form: `Time`, `OS.get_ticks_*`, the engine's frame counters and time scale (`Engine.get_physics_frames`, `get_physics_interpolation_fraction`, `Engine.time_scale`), the frame's delta, timers and tweens (`create_timer`, `create_tween`, `Timer`), `await` (the rest runs outside the tick, its state in no member) and deferred calls (`call_deferred`, `set_deferred`: they run after the frame), and `_process` or `_physics_process`;
- **the dice**: the engine's global ones (`randf`, `randi`, `randomize`) and a generator of its own (`RandomNumberGenerator`): chance comes from `sim` ("Chance");
- **the engine's maths** (`sin`, `atan2`, `pow`, `Vector2.rotated`, ...): `DMath`'s ("Maths");
- **input** other than the seat's frame: `Input`, the input layer (`InputManager`, `LocalInput`, `PlayerInput`) and the mouse ("Input"); the seats joined come from the frames service (`Frames.joined_seats`);
- **the picture**: the window and a camera (`get_viewport`, `get_visible_rect`, `Camera2D`): the room's size is `RoomBase.size_in`, and the game has no view of its own (the camera is each machine's);
- **instance ids** kept: `get_instance_id` only on a line that touches a DERIVED member of its script (a lookup by equality, `_target_row`), never as state ("Contract").

**View code inside a simulation script** is a function named in its `VIEW` list, beside its view members (the projectile manager's `_process`, `update_draw` and the sparks it gives off); a single line that only draws says `# view: why`. The test reads neither, and `tests/core/test_determinism.gd` ("the view stepped thrice") plays scenes with every view function run three times between ticks: a view function that writes state parts them. The party's camera is Feel's (`gameplay/feel/party_camera.gd`): it eases towards Coop's view (`view_fitted`) on real time.

## Contract

- **State by default.** Every member of a simulation script is state, except what it lists:
  - `const DERIVED: Array[StringName]`: references to services, caches, scratch reused within a step, instance ids: anything set up again or rebuilt from state. Never walked.
  - `const VIEW: Array[StringName]`: what only the drawing reads and writes. Never walked.
  - `const REFS: Array[StringName]`: references to bodies it does not own that are state all the same (an AI's target, the body a shot is stuck to, the bodies a zap is due on, the row bodies of Combat). Walked as **who** they point at, never entered: an actor by its id, anything else by what it is, until N5 gives every body an identity of its own. In an array only the filled entries are walked, each with its index, so a slot-sized array that is nearly all empty costs one engine call; an array that holds only bodies (and empty entries) is one leaf of their actor ids, which a report names by index (props W3b).
  - `const SPARES: Array[StringName]`: free lists of spare records, each set whole when it is taken (Spells' spare launches): walked as their size alone (N3c).
  - `const BY_ACTOR: Array[StringName]`: tables an area keeps by actor id that grow with the actors (Spells' builds by caster): state, which the hash walks id by id as parts of their own, beside each actor's body ("The hash", props W3). The script hands each id's part over: `actor_parts() -> int` (ids 0 to it less one) and `actor_part(id) -> Array` (empty for an id with none: no area then). A part may leave out what follows from what it holds (Spells' resting caster: its current spells are its builds' nodes); then the script says what that stands on with `actor_part_problems() -> PackedStringArray`, which `tests/core/test_state_walked.gd` asks at every walk of every card. A BY_ACTOR member is in no other list. A walk of the area itself and a snapshot take them as any member.

  A list is named after its kind, or after its kind, `_` and a name of the script's own: a script that extends one with a `DERIVED` list cannot declare `DERIVED` again (GDScript forbids it), so it declares `DERIVED_BEAM`. The lists of a script and the scripts it extends are all read. A look or another view script inside a simulation folder says `const VIEW_ONLY: bool = true`; the walker never enters it, and a member that holds one is in VIEW or DERIVED.
- **Made once, or waiting** (N3c, for the hash's cost): a script whose objects are made whole and never changed after (a compiled staff, its casts, groups and spells, a cast's sense) says `const FROZEN: bool = true`; wherever one is met it is one leaf, the hash of its members, worked out once (`tests/core/test_state_walked.gd` walks every card with `verify_frozen`, which names one that changed). A record a carrier keeps per row, nearly all waiting (a dash's or a beam leg's homing), has `func idle() -> bool`, true while its state is a fresh one's: it is one leaf then.
- **What state may hold** (`state_walk.gd`, `StateWalk`): values, packed arrays, arrays (a typed array of plain values in one go; in one with empty slots, only the filled ones, each after its index: a carrier's per-actor table is mostly empty), dictionaries (keys sorted, StringNames by their text: the engine's own sort orders them by address, which differs between machines; a key is a value, never an object), objects of scripts (walked member by member, once), a simulation node the holder owns (an actor's components: its descendants, with `position` and a body's `velocity`), a reference to a simulation node with an int `id` (an actor: its id), resources from files and scenes (their path: data cannot desync) and `RandomNumberGenerator`s (seed and state). Anything else is a problem, named with its path and the fix: a service (DERIVED), another body without an id (REFS), a Callable, a Signal, an RID, an engine object.
- **What the walker cannot see** is checked by reading the source (`tests/core/test_state_declared.gd`): a `static var` belongs to no object, so it is listed in DERIVED or VIEW (a cache, a test switch) and never holds state; what simulation code may not call is "The line" (`tests/core/test_sim_rules.gd`). A seed nobody chose (a run started with none) comes from `SimSeed.fresh()` (`sim_seed.gd`), the one place the simulation reaches the engine's global generator; N11 makes it the session's seed.
- **The hash** (`sim_hash.gd`, `SimHash`): `SimHash.areas({name: object}, walk)` gives one 64-bit hash per area (problems in `walk.problems`), `SimHash.whole(hashes)` the game's, `SimHash.area(walk, name, object)` one area. The caller hands it the areas: the game's are named by the Tick (`Tick.state_areas()`: "Sim", every area joined, the actor table, every actor's body by id), a test world's by the test; areas never reach into each other. The walk appends an area's leaves to one array (`StateWalk.values`, no call per leaf; a member declared a plain value is appended as it is), hashed by its bytes in one call; a packed or typed array in it stands as its type, size and the engine's `hash()` of it, which hashes -0.0 as 0.0 and every NaN alike inside an array (a single value is hashed by its bytes). Its cost grows with the shot cap, not the live shots: the projectile manager and the actor table hash in about 2 ms at the desktop cap (6,000) and 15 ms at 100,000, on the owner's machine, headless. The whole game's grows with its bodies (each walked member by member: about 0.2 us a plain member, a few us an object or a reference; the stress runs' numbers are in docs/milestones/online-ready.md, N3c), so a check of it is spread over ticks: `SimHash.slice(Tick.state_areas(), slice, slices)` is one part, a service one to a part and a body by its id, every machine hashing the same part at the same tick. A body at rest (still and as it was made: `Actor.rest_leaf`, props W2) is one leaf of where it stands and aims, its size, health and staff on show, not its members: a standing prop hashes in about a sixth of the time. Only the hash does so; a snapshot saves every body whole. An area that keeps state by actor id (`BY_ACTOR`: Spells, by caster) is hashed as **parts** (`SimHash.ActorPart`, props W3): the area less those members under its own name, and one part an id that has any ("Spells 7", `actor_part(7)`), which `slice` puts in the part of that actor's body, so a crowd of casters no longer weighs on the tick Spells is hashed in, and a check that parts names the caster. Only `SimHash` makes parts and calls the area's `actor_parts`/`actor_part` (`split_by_actor`, `slice`, `areas`, which the desync report uses with a sink); the walker walks an area with or without its BY_ACTOR members (`without_by_actor`), or a value it is handed (`walk_value`, `values_of`), and knows nothing of parts. `SimHash.of` and a snapshot take an area whole. A live caster's generations are named ("s0g3"), so a report names the field that differs. A caster with nothing of its builds alive is its four builds as installed (each FROZEN, one leaf) and its last infusion; its generations, live counts and older builds' spells join only while something of them is alive.
- **The desync report** (`desync.gd`, `Desync`): `capture(areas)` after each tick records the hashes, and every leaf of one chosen tick (`Desync.new(tick)`), with paths for that tick only (a path per leaf every tick made a determinism test 3.5 times slower); `Desync.first_parting(a, b)` is the first tick two runs part, and `Desync.compare(a, b)` names that tick, its areas and each member that differs, with both values (a packed array's first differing index).
- **Never in a normal build's tick.** The walker, the hash and the report run in tests, tools, replays and later the netcode only.
- **Instance ids are not identities** (N5). They differ between machines and runs, so the simulation never keeps one as state. A body's identity is its actor's **key** (`Actors.key_of(id)`: the id and its birth, the count of opens this run, so an id handed out again is another key; the births count from 0 at each run's start). The projectile manager names each target by it (`_target_key`, handed over by Combat; `key_of(node)`, `target_of_key(key)`), and what a shot or a spell keeps of "that body" is the key: a homing target, the hit memory, the body a payload spares, a chain's last body, a zap's rolls, an AI's target and the team board's attacks. An instance id may still find a node by equality, as a DERIVED lookup (`Actors._node`, `Combat._row_by_node`, the manager's `_target_id`), never as state, an order or a seed.

## The tick (N3a)

- **One driver.** The autoload `Tick` (`tick.gd`) runs every tick: the input frames (`Frames.tick`), then the areas' steps in its written order, `Tick.STEPS`: the services (the projectile manager, Spells, Combat, Entities), every actor's body by actor id (`Tick.BODIES`, the Tick's own: `Actor.tick_step`, its step, then its move), the items on the ground (the Items area: what is in reach of whom, items I6), then the run's rules and timers (Flow's, Coop's). It is the order the scene tree gave them before, so the game plays as it did; only the bodies go by id now, not by when they joined the tree.
- **Areas join the tick; the tick knows none.** An area joins in its `_ready` (`SimArea.join(self, &"Projectiles")`, `sim_area.gd`) and names its steps (each under a key of `Tick.STEPS`, a Callable taking `delta`), its run's start (`renewed_by(begin_run)`, or `fresh_because(reason)`) and the rules it takes (`takes_rules(take_rules)`). The Tick calls those Callables in its written order; the keys are only names, nothing is called by name and no area's method is the Tick's business. Only the game's autoload (`/root/<name>`) joins the game's Tick, so an area a test makes is stepped by the test alone. No area and no body has a `_physics_process` or a `_process` for the game; drawing stays in `_process` (view: the projectile manager's `update_draw`, in its `VIEW`; Feel's party camera; the looks). A new area that steps adds its key to `Tick.STEPS` (and `RUN_ORDER` if it is renewed) and joins.
- **Still bodies are skipped** (props W2, docs/milestones/props.md): a body that no controller drives and that has no Mover is still (`Actor.is_still`; a prop), and the Tick never steps it: one read of the actor table's `still`, which the body sets when its id opens and at every change of driver (`Actor._tell_driver`, the one place a driver changes). It is a rule of the game, not a shortcut: a still body takes no hold or protection (its step would spend them), its pools do not refill, and Combat, not its step, holds a slowed actor's wind-ups back. A possession gives it a driver, and it is stepped while that lasts.
- **What the tick steps:** an area while it is `ticking` (`Tick.set_ticking(node, on)`: a test or a benchmark that steps it by hand turns it off) and its node can process (its process mode: the tree is never paused while the tick steps, below); a body while its `Actor.ticking` is on (a decoy, which Entities steps, is off; so is a body a test steps by hand). The engine's processing flags mean nothing to the tick.
- **The clock is `sim.tick`:** the ticks run since the run began, so during a tick it is that tick's number; the Tick counts it after each tick (`Tick.count` reads it). It is state, so a snapshot restores it with the rest (N10).
- **`ticked`:** the Tick's signal after every tick has stepped (held and stopped ticks too), for whoever follows the game tick by tick from outside the simulation (the netcode's sessions send the tick and hash its state there, `net/`). Nothing in the simulation hears it: an area that steps joins `STEPS`.
- **Time:** every step gets `Tick.DT` (1/60 s; `tests/core/test_tick.gd`), always: the game never scales the engine's time (N4). A physics step runs the ticks the frames service says (`Frames.begin_step`, called first in every step, also under the picture's pause): one, but none while a live replay waits for its next tick and up to three while it catches up (below, "Input"). A slow frame runs up to `max_physics_steps_per_frame` physics steps, each tick of `DT`. The bodies' `move_and_slide` still takes the engine's physics step until N6, so the engine's tick rate and time scale stay the project's (a faster test runs at `--fixed-fps`, unthrottled).

## Stops and holds (N4)

- **The game's, in its state.** `sim` holds them (`Sim.hold_left`, `Sim.stops`, hashed as "Sim"): a **hold** stands the whole simulation still for a number of ticks (`sim.hold(ticks)`: a downed wizard, a boss's death; a longer one replaces a shorter one, they never add up), a **stop** until its reason goes (`sim.stop(reason)`, `sim.go(reason)`; each reason is its area's: `Coop.MENU_OF`, the pause menu, one reason a seat, by the command `pause_requested`, and let go when that seat leaves too, so a machine that leaves with its menu open never leaves the others stopped; `Coop.PAD_OF`, a seat's unplugged gamepad, one reason a seat, by the command `pad_wait_requested` from `core/input`, let go when the seat has a gamepad again or leaves). While the sim is held a tick runs the input frames and nothing else; while it is stopped, the frames and only the steps that run through every reason it is stopped for (`steps(key, call, own_stops)`: a step through a stop of its own area, never through the menu); the ticks count. A tick that stood still hands its presses on (`Frames.stood`), so a tap made then is not lost.
- **The picture follows.** The Tick pauses the tree while the sim is stopped (not while it is held: the drawing runs on through a hold) and lets it go when the sim goes, right after a tick's commands apply, so the tree is never paused while the tick steps; nothing in the simulation reads the tree's pause. A tree paused while the sim goes (the pause menu while a replay plays) runs no tick: the replay waits.
- **Local holds** (a hit's, a kill's, a cue's) are bodies' and shots', not the tick's: Combat's `HitStop` (`gameplay/combat/hit_stop.gd`) decides them, `Actors.hold` keeps them and a body's rest after one, spent by its own steps (`spend_hold`; a step a hold covers part of moves the body for the rest of it), and `Projectiles.freeze_shot` a shot's. Feel only draws them.
- **Nothing in the simulation reads the camera, or knows of one.** The camera is view, and each machine's own: Feel's party camera holds the wizards of the seats played on that machine (`Frames.seats_here`, asked by the view only; everyone with none) and eases as it is drawn, on real time. So two machines playing one game show different parts of the room, and the game is the same on both.

## Chance (N3c)

- **One source.** The simulation's chance comes from `sim` (`sim.gd`, `Sim`): the Tick owns the game's (`Tick.sim`: the tick, and the run's seed, which the frames service deals at each run's start: `Frames.next_run_seed`, a replay's while one records or plays, else random, `SimSeed.fresh()`). An area or a body holds it as a member `sim` (DERIVED), set by whoever makes it, else found (`Sim.found(node)`: the Tick's in the tree, else a shared one at seed 0); a test hands its own (`Sim.seeded(7)`). No simulation script keeps or makes a `RandomNumberGenerator` (`tests/core/test_state_declared.gd`, `test_sim_rules.gd`).
- **A roll is named, not drawn.** `sim.chance(purpose, key, counter)` (and `chance_int`, `chance_range`, `bits`) is a hash of the run's seed, the purpose (`&"scatter"`), the key (whose: a cast, a seat, an actor) and the counter (which of its rolls). No generator holds state, so a new roll in one system never shifts another's; the counters a caller keeps are its state, reset with it at a run's start. The same name gives the same roll, so a caller counts its rolls. The hash is the engine's of a `Vector4i` (murmur3), integer code, the same on every platform.
- **The tick is not in it.** A roll is the same whenever it is made, so an area a test steps by hand rolls as it does in the game; a caller that rolls once a tick names `sim.tick` itself.
- **Who rolls:** Spells' scatter and spread (`&"scatter"`, keyed by the cast; a later firing by its launch), the AI brain (`&"brain"`, keyed by its actor). Zaps, homing picks and the tails' hashes were already hashes of the shot (`Spells.zap_hash`, `tail_hash`): they stay so.

## Maths (N7)

- **The same bits on every platform.** The engine's `sin`, `cos`, `atan2`, `exp`, `log`, `pow`, `ease`, `Vector2.from_angle`, `rotated`, `angle` and `angle_to` call the platform's C library, which differs between Linux, Windows and the web in the last digit now and then (N2b found exactly that), and a game played online would part there. Simulation code calls `DMath` (`dmath.gd`) instead: the same functions, built from `+ - * /` and `sqrt` (and the exact `floor` and `fmod`), which IEEE 754 rounds the same everywhere.
- **Native, with a twin.** Each `DMath` function runs the native module's (`DMathKernel`, `native/src/dmath.h`) when it is loaded, else its GDScript twin, the same operations in the same order: `tests/core/test_dmath.gd` compares the two to the bit and both to the engine (within 2 units in the last place; tan, asin and acos 4). The kernels call `dmath.h` directly where the GDScript they stand for calls `DMath`. A Vector2 helper works in doubles and rounds to the vector's floats once.
- **Checked from the source:** `tests/core/test_sim_rules.gd` fails on engine maths in a simulation script. A view-only script keeps the engine's; a line in a simulation script that only draws says so, `# view: why` (`tests/core/fixtures/sim_view_fixture.gd`).
- **Not covered here:** `+ - * /` and `sqrt` inside the engine's own code (a Vector2's `normalized`, `length`, `lerp`) are correctly rounded everywhere already; a node's `rotation` turns its transform with the engine's sin and cos (drawing only: no physics body is left since N6, whose bodies move by `WallSlide`).

## Order (N3c)

What the simulation goes through, it goes through in an order of its own, never the tree's or a signal's connections': the bodies by actor id (the Tick), the shots by slot, Combat's rows by row, Entities' rows by birth, Coop's wizards by actor id. An event several simulation areas hear goes to autoloads, in the project's autoload order; one a body hears (a mover's `target_move_requested`, a caster's `mana_spend_requested`, an actor's `possess_requested`) names the one body that acts on it.

## A run's start (N3b)

- **Every run starts from a fresh game's state.** When a run starts (Flow's `start_run`, once the last run's world is gone and before the new one is made), `Tick.begin_run` counts the clock from 0 again, takes the run's seed and rules from the frames service, hands the rules to every area that takes them, and calls each joined area's `begin_run` in `Tick.RUN_ORDER`: Entities first (it frees the last run's decoys, bodies outside Flow's world that the manager and Combat still hold), then the other services; the actor table last. No area is renewed while a body that leaves later is still registered in it. A run then plays the same whatever ran before it in the game, and a replay recorded in any run plays the same in any other (`tests/core/test_replay_game.gd`, "after other runs").
- **An area's `begin_run`** ends what it holds and renews itself, nothing more:

  ```gdscript
  func begin_run() -> void:
  	clear()                 # its shots, rows, entities end (their events go out)
  	SimFresh.renew(self)    # every state member as a new object of its script has it
  ```

  `SimFresh.renew` (`sim_fresh.gd`) resets what `StateWalk` walks, so a member added later is reset too, with no list to keep. Its rules, in its class doc: `RUN_KEEPS` stay; an object held by a member or in a dictionary (a carrier, the AI board every brain shares) stays the same object and is renewed in turn; an array is the blank's, its objects too (a pool), and references into it follow (`Spells._ray` is the first of `_rays` again); DERIVED and VIEW are left alone.
- **Settings stay:** what is the session's, not the run's (the shot cap, a benchmark's budget), a script lists in `const RUN_KEEPS: Array[StringName]`, read like DERIVED (`tests/core/test_state_declared.gd` checks each name is a state member).
- **The run's rules** (N11, `session_rules.gd`, `SessionRules`): every setting that changes the game (the shot cap, the hit-test work a step may do, the shots a trigger's fires may make in a step) is one of the run's rules, in `sim.rules`. `Tick.begin_run` takes them from the frames service (`Frames.next_run_rules`: a replay's while one records or plays, else a copy of this machine's, `SessionRules.machine()`) and hands them to each area that takes them (`takes_rules`) before any is renewed; the area keeps the member it sets in `RUN_KEEPS`. Each bag's capacity is one too (`bag_staffs`, `bag_cards`, `bag_relics`, `bag_potions`, 0 for no limit, `bag_capacity(bag)`; items I4), which an inventory takes at its start. A replay's header carries them. A new setting the simulation reads becomes a rule: its member and a row of `SessionRules.FIELDS` (its name and range; copying, comparing and the header's bytes follow), and the area's `take_rules`. One that only changes the look is VIEW and never state. A change in a run is a command (`shot_cap_requested`), never a machine setting heard by the simulation.
- **Lists that grow together are listed together.** Scratch kept in several lists grown at once, by a check on one of them (a ray's lists per nesting level, a sweep's results), is all DERIVED or all state: a run's start empties state and keeps DERIVED, so a split leaves the check saying there is room the others no longer have (N3c's stress runs found two).
- **What fails loudly:** a simulation autoload that does not join the Tick, or joins neither renewed (`renewed_by`, and in `Tick.RUN_ORDER`) nor excused (`fresh_because`), or steps under a key outside `Tick.STEPS` (`test_tick.gd`); a node out of the tree that `renew` would drop (a pool of bodies: free it before, as Entities frees its decoys).
- **What it cannot see:** a cache in DERIVED that follows the state must be emptied by the area's `clear`; an object in an array that something outside the area holds on to is replaced, so keep such an object in a member or a dictionary. A cache that would carry a run's answer into the next (a compiled staff outlives a run) is DERIVED.
- **Feel**, which is view, plays the moments' looks; their holds are Combat's (`HitStop`, N4). The cue names and the reaction repeat both use are `CueBase`'s (`REACTION_CUE`, `REACTION_REPEAT`, `reaction_cue`), so the two always agree.

## Snapshots (N10)

- **The whole game, by the walker's plan.** `Snapshot.take(areas, world)` (`snapshot.gd`) keeps every state member `StateWalk` walks, by the same plan (`StateWalk.plan`), so a member added later is saved and loaded with no code of its own; `snapshot.restore(areas, world)` makes a world of the same kind (the same one, or a fresh one: a player joining) as it says. `areas` is `Tick.state_areas()` in the game, a test world's otherwise; `world` is the node the bodies' parents are named under (the tree's root). A snapshot holds data only (values, arrays and dictionaries with their types, objects member by member) and content and FROZEN objects as themselves, so it restores into any world, any number of times.
- **What it is checked by:** `tests/core/test_snapshot.gd` (the scripted scenes: a fight, a storm and a possession, each snapshotted and restored into a fresh world, the fight, the storm and a decoy fight rolled back twice from one snapshot, and plain objects piece by piece, `restore_nodes` among them), `tests/core/test_snapshot_game.gd` (a sandbox run and a wave in every room on the real autoloads, recorded with a snapshot; a fresh game starts the replay's run, restores it and plays the replay on from the next tick, `Frames.seek`, as a joining player would), and `tests/core/test_content_determinism.gd` (N12: every card and enemy the registry finds, each in a scripted fight of its own, `tests/core/content_fight.gd`, played twice and through a snapshot taken at a tick of its own). Every tick from the snapshot on agrees in every area, and the desync report names a member that parts: one wrongly in DERIVED, or a DERIVED one that follows the state and is not rebuilt.
- **References** (REFS, and a node another holds) are kept as the actor id the actor table keeps the node under, and the path under it (a controller in a body); an object of a script by its number where the snapshot holds it. A reference to a node no actor id names is a problem.
- **Bodies** (`StateWalk.is_body`: a node with an actor id) are made again from their scene (`scene_file_path`), or their script for one built in code, under the same parent path (so a test world names its nodes the same in every world: a node's automatic name differs), with the simulation nodes added to them in play (`StateWalk.added_in_play`: a possession's puppet, a boss's phases), which the walker walks with the body. A body is given its state before it enters the tree, so its own `_ready` wires it (its components, its id, its controller) as when it was first made; then everything is written again.
- **What an area does for it, by method name (none writes save code):**
  - `func rebuild_derived() -> void`: its DERIVED members that follow the state, set up again after a restore (Combat's and the projectile manager's lookups from a node to its row, a controller's signals, which follow the body it drives: `ActorController.bind`/`unbind`). Called on every object restored that has it, the innermost first. A DERIVED member nobody rebuilds keeps the restored world's own: right for a service or scratch, wrong for anything that follows the state, which the snapshot tests find.
  - `func remake_body(name: StringName) -> Node`: on the node a body built in code lives under, when that node builds such bodies (Entities' decoys: their components, mind and look made in code): the body named `name` made new, out of the tree, for the snapshot to write and add. Without it a body built in code is its script's `new()` with the simulation nodes it had, by name and script, and no look. A body built in code is matched by its name as well as its actor id (ids are handed out again: after the snapshot another row's decoy may hold the id), so its name must say which it is (Entities' `Decoy<row>`).
  - `func restore_nodes() -> void`: the nodes it makes from its state that are no bodies (bare nodes registered as plain bodies), set in the actor table; the outermost first (a holder sets up what it holds, then that one makes its nodes). Nothing in the game has one now; it stays for an area that makes bare nodes.
- **Shared by identity:** an object one copy of which serves many (an AI behaviour, which a brain knows by which copy it is) is FROZEN, so a snapshot keeps it as itself (`AIBehaviour`; the rolls of a brain whose running behaviour was a copy parted the wave). A shared read-only object that is not known by its copy is FROZEN too, so a snapshot keeps it as itself and the hash sees what it holds, not which object it is (`HitProfile`: a relay shot holds its compiled spell's own; a snapshot that copied it as state gave the restored shot an equal copy, and echo parted on that alone, N12). The hash cannot tell two equal FROZEN objects from one, so nothing may branch on which copy a FROZEN object is unless the copies differ in what they hold.
- **Numbers a machine hands out as it meets things** are not state: which draw batch draws a card's shader (`register_body`: numbered in the order a machine first meets each, Feel's among them) is VIEW in the projectile manager (`_body`), and Spells gives the live shots theirs again (`rebuild_derived`).
- **Dictionaries keep their order** (the order they were filled in, which a loop follows: Spells steps its carriers so), though the hash walks their keys sorted. **Content** is a resource from a file; a resource made in code is state like any object.
- **What it does not hold:** the input (the frames service's tape, a test stage's casts, presses carried through ticks that stood still): a join takes the frames after the snapshot (`Frames.seek`). A bot's queries fill the services' caches, which are state, so a run of bots goes on the same only with the same bots watching from the same state; a joining machine never runs the host's bots.
- **Not yet:** the bytes a join sends (a strict decoder; scripts and content named by path and checked) are the netcode's. FROZEN objects are kept as themselves in a snapshot, and some are made in play (a relay's merged `HitProfile`), so a join sends them by value.

## Input (N2)

- **One input path.** The simulation takes input from `InputFrame`s only (`input_frame.gd`): one seat's input for one tick, its move (a signed byte per axis), its aim (a 16-bit angle, or keep), the staff buttons held and pressed, captured (an overlay of the seat is open), and the tick's commands. A seat's `PlayerController` builds its actor's intent from its frame; nothing in the simulation reads a device, the mouse or the camera. Devices (`LocalInput`, core/input), bots (`FrameSource`, `frame_source.gd`), replays and later the network all produce frames.
- **The frames service** (`frames.gd`, the autoload `Frames`): the Tick calls its `tick` first in every tick, so it is the tick's start. It builds each seat's frame (from the replay played, the seat's source, or its device; captured holds a source still), records it when a replay records, and applies the frame's commands. `frame_of(seat)` is the tick's frame, read only. A seat aiming with the mouse aims from its pivot (`set_aim_pivot(seat, callable)`: its PlayerController tells it its wizard's hand), so the input layer knows no body. It also says how each run starts (`next_run_seed`, `next_run_rules`, `next_run_party`) and keeps this machine's rules (it hears the "Max shots" setting).
- **Commands at the tick's start.** The HUD's requests the simulation hears (`InputFrame.COMMAND_NAMES`) are commands: the bus hands each to the frames service (`Events.command_sink`), which puts it into its seat's next frame and applies it when that tick starts (`Events.apply_command`); the simulation hears them through `Events.listen`, never by connecting to the signal. A frame speaks for its own seat only (the seat is not in the command). A device's join and leave are in the frame too (JOIN, LEAVE): they happen as the device joins (Flow and Coop read the joined seats at a run's start), and a replay played joins and leaves its seats at their tick. The requests that start a run (`play_requested`, `sandbox_requested`) are not commands: they are a replay's start.
- **The bytes** (`InputFrame.to_bytes`, `Replay.to_bytes`) have strict decoders: every size and value is checked, an id is letters, digits and `_` only (never a path), nothing is left over, no `bytes_to_var`; a bad frame or file is rejected whole and says why (`decode`).
- **What a run takes along** (`party_loadout.gd`, `PartyLoadout`, of `player_loadout.gd`, `PlayerLoadout`; items I4, docs/milestones/items.md): each seat's player loadout, the whole player: its counted bags (by bag name, each stack an id and its copies), every staff it owns under its number with its id and card ids by slot, and its hands (by hand, a staff's number or none). Written in tagged sections (bags, staffs, hands, each its tag and length), so a later section (a name, colours) is added beside them without changing theirs; a section it does not know rejects it. Plain data that knows no item: the inventory writes its own (`Inventory.loadout`) and takes one back (`Inventory.take_loadout`). The game says what a run starting now would take (`Frames.set_party_source`, Flow's: in the hub every wizard's loadout, anywhere else nothing), a recording begun writes it into its header, and a run that starts reads it back (`Frames.next_run_party`: the replay's on the deck, else the game's now). So a hub begun anew for a joining machine keeps every wizard as it was on every machine, though only the host had them. Read as strictly as a frame: plain ids, every count, number and length within the limits the writers hold to as well (`PlayerLoadout.MAX_*`).
- **Replays** (`replay.gd`): a run's build, content (a hash of every content id), seed, start (the request and the seat), seats, rules and what it takes along (format 5; 6: each carried staff's own id; 7: the players' loadouts and the bags' capacities among the rules, items I4), then every tick's frames, inputs only (format 3: the game's stops are its state, so a tick carries no pause mark and a replay stands still where its recording did). `Frames.record(start, starter, run_seed)` starts a run and records it (a random seed when `run_seed` is 0); `Frames.play(replay)` joins its seats, starts its run the same way and feeds its frames until they run out (live input and commands are dropped meanwhile). The replay on the frames service's deck is a `ReplayTape` (`replay_tape.gd`): where it is, and the runs it starts, whose seeds are dealt from the replay's seed in turn and whose rules are copies of its own. Nothing about it is global. Files live in `user://replays/` only (`save(name)`, `open(name)`).
- **A live replay** (netcode spike S1, [docs/milestones/netcode-spike.md](../../docs/milestones/netcode-spike.md)): a replay that grows while it plays, the online client's. Its header comes alone (`Replay.header_bytes`, read back as a replay of no ticks), then its ticks one by one (`tick_bytes` out, `add_tick_bytes` in, each checked by the file's decoder). Whoever plays it is a `LiveFeed` (`live_feed.gd`, the seam the client session extends, as a bot extends `FrameSource`): `Frames.play_live(feed)` plays the feed's `replay` and starts it as `play` does but refuses another build too (online it would part). The Tick calls `Frames.begin_step` first in every physics step: the feed's `pump` adds the ticks that arrived (and sets `closed` once no more will come); the feed's `local_seats` (this machine's) build their frame from their device or source, with their commands, and it goes to the feed's `send` with the replay's next tick, one a step, also while the replay waits (the other machine hears this one at its own pace; which host tick a frame is for is the feed's); then the step runs the ticks the feed's `ticks_to_run` paces, never more than are there and none while none is (the picture holds; nothing in the simulation moves). The replay's frames are the game's, so a local command applies when it comes back in them. Once its feed is closed it ends when played out. A replay, file or live, ends at the start of the step after its last tick, so that tick steps with the replay's seats like every other. `hears_commands(seat)` is false while a replay plays but for a live replay's local seats (the pause menu then stands the picture still instead of sending `pause_requested`). A bot as a local seat would part the run (its queries fill caches that are state, above); a person's input does not. The feed's `local_seats` is read every step, not once: the feed may change it while the replay plays (online lobby L2: the host gives this machine a seat, or takes one back). **A run the game asks for itself** (`Frames.restart(start, starter)`; online lobby): Flow asks for the hub's start when a run ends. It is sent at the start of the next physics step, never inside a tick, so every machine starts it between the same two ticks; a run being recorded begins a new recording there (`recorded_anew`), a replay from a file ends there, and a live replay waits for its feed to bring the next recording (`play_live` again, taken by `begin_step` in its stride). **Back to the main menu** (`main_menu_requested`, this machine's own leaving, never a command): what is recorded or played ends, and a `restart` not yet begun is forgotten; the seats' waiting commands are kept (the pause menu's own unpause is one).
- **Seats are the simulation's** (`seat_joined`, `seat_left`, sent by the frames service only; Coop hears them, Flow reads `Frames.joined_seats` at a run's start): offline as a device joins and leaves, while a replay plays (a file or live) as its frames say, at their tick's start, whatever this machine's devices do (a pad plugged in during a replay seats nobody until it ends; an online client's own seat leaves when the host's frames say so, and its device stays). A replay's seats get virtual devices for the HUD, which the frames service remembers and gives back when the replay ends or is sought past their leave; a real device or a bot's is never sent away. A `FrameSource` never seats: it may pass on another machine's commands, but a JOIN or LEAVE it writes is dropped, since a seat joins and leaves through the input layer (the host's session for a client's seat will join and leave its virtual device). Nothing in the simulation hears `device_joined` or `device_left`.
- **What a replay does not hold yet.** A bot reads the game through queries that fill the services' caches, and those count as state (the projectile manager's threat grid and target table), so a bot's run replays exactly with the bot watching again (a source set while a replay plays is asked each tick and its frame dropped); a person's input reads nothing of the game but where the hand is. Shots keep homing targets and skips by instance id (`_home_target`, `_skip_id`, A5): a run with homing parts until N5.

## Allowed files

Claude only, like all of `core/`. Typed GDScript, no banned APIs.

## Steps

A new member of a simulation script, by what it holds:

| It holds | List | Examples |
|---|---|---|
| the game: a value, a packed array, an object of a simulation script, an actor it owns | none (state by default) | `Combat._health`, `Actor.intent` |
| a service, or a node the area sets up again | `DERIVED` | `events`, `projectiles`, `Flow.world` |
| a cache, scratch refilled within a step, an instance id, a switch that gives the same game either way | `DERIVED` | `Spells._zap_near`, `Combat._row_by_node`, `ProjectileManager.native` |
| another body the game would miss if it were lost | `REFS` | `AIBrain.target`, `ProjectileManager._stuck_to` |
| what only the drawing reads and writes | `VIEW` | `ProjectileManager._drawn_seq`, `Actor._looks` |
| a free list of spare records, each set whole when taken | `SPARES` | `Spells._pending_free` |
| a table kept by actor id that grows with the actors, and is walked by id (with `actor_parts`, `actor_part`) | `BY_ACTOR` (it stays state) | `Spells._installed`, `Spells._profiles` |
| a sum or count kept by the same functions that write the table it sums (so it is never rebuilt) | none (state): exact in a snapshot with no `rebuild_derived` to forget | `Spells._caster_live` |
| a setting of the session a new run keeps (in an area with `begin_run`) | `RUN_KEEPS` (it stays state) | `ProjectileManager._cap` |
| a setting that changes the game | a field of `SessionRules`, set by `take_rules`, and `RUN_KEEPS` | `shot_cap` (`ProjectileManager._cap`) |
| a setting of this machine that only changes the look | `VIEW` | `ProjectileManager.tailless_particle_cap` |
| a lookup or a connection that follows the state (a node's row, the body a controller hears) | `DERIVED`, and set up again in `rebuild_derived()` ("Snapshots") | `Combat._row_by_node`, `ActorController._bound` |
| a node made from the state that is no body (a bare node registered as a plain body) | made again in `restore_nodes()` ("Snapshots") | none in the game now |

And around it:
- A `static var`: `DERIVED` (a cache, a test switch); it never holds state.
- A look or another script that only draws: `const VIEW_ONLY: bool = true`. A function of a simulation script that only draws: its name in `VIEW` ("The line").
- A script whose objects are made whole and never changed after, or one copy of which serves many (known by which copy it is): `const FROZEN: bool = true`. A per-row record that waits most of the time: `func idle() -> bool`.
- A computed property (a getter over another member): `DERIVED`, or a restore writes it (`Flow.sandbox`).
- Chance: `sim.chance(purpose, key, counter)` with a counter of its rolls as state (above, "Chance"); a `sim` member in DERIVED. Time: `delta` and `sim_time`, never a clock.
- Angles, curves and turns: `DMath` (above, "Maths"), never the engine's `sin`, `pow` or `Vector2.rotated`.
- A list sits above the script's first member, with its one-line comment (`## Not state: ...`, `## State as who they point at: ...`); a subclass of a script with a list names its own (`DERIVED_BEAM`).

The tests say what is missed: `tests/core/test_state_declared.gd` from the types and the source (every script and inner class), `tests/core/test_sim_rules.gd` what its code may not call, `tests/core/test_state_walked.gd` in running games (three scenes and every card), and `tests/core/test_determinism.gd` any member that parts between two runs of the same scene. Each names the file, the member and the list it belongs in.

## Review questions

- Is every name in DERIVED really rebuilt or set up again, not state that would be lost? A body the game would miss goes in REFS.
- Does a new scene in `tests/core/sim_scenes.gd` play the same twice?
- Does any simulation code read a device, the mouse or the camera, or connect to a command's signal instead of `Events.listen`?
- Does new simulation maths go through `DMath`, and a kernel's through `dmath.h`, the two the same to the bit?
- Does a new DERIVED member follow the state (a lookup by node, a connection to the body driven)? Then the script's `rebuild_derived()` sets it up again, and the snapshot tests cover it.
- Is a new area that keeps state between runs made fresh at a run's start (`renewed_by(begin_run)`, a `begin_run` calling `SimFresh.renew`, in `Tick.RUN_ORDER`), and is each name in its `RUN_KEEPS` a setting, not the run's state?
