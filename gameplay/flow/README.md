# Flow

## Purpose

Room sequence, door voting, transitions and waiting for builders.

Built in M3 (see "Gameplay sub-areas" in docs/PLAN.md).

Players in the spell builder never block the others: the rest keep playing.

## Contract

- **Public entry script:** `gameplay/flow/flow.gd`. Other code uses only this script and the events it sends and listens to; nothing else in the folder is public. It is the autoload `Flow` (registered in `project.godot`).
- **What exists (M1 slice):** on `play_requested` it asks `core/registry` for the room and enemy named by `room_id_to_play` and `enemy_id_to_play` (defaults `arena_01`, `ember_imp`; players come from `wizard_scene`) and the hands of the run's mode (`staffs_for_mode()`, owner 2026-11-01: one staff file per setup, used as it is, never copied or changed, in every build channel): in Play and the hub the first two basic staffs of `STARTER_HEADS`, curl on RB and star on RT, each its own head, and the other two hands empty (`START_HANDS`, items I2: players start with two staffs; moon and crystal wait for the items); in the sandbox the `dev` staff (`DEV_STAFF`: 20 slots, no delay, a million mana and regen) on every button; all from `wizard` in the registry; a missing one starts no run: it logs a warning and stays idle). `start_cards` are four lists of card ids (default: A `dash`, X `bolt`, Y and B empty); **each mode's setup** (owner, 2026-11-05): with its staffs and start cards a new wizard gets its mode's bag (`bag_for_mode()`, through `seat_wizard`): Play `play_bag` (`PLAY_BAG`: `dash`, `bolt`), the sandbox and the hub every spell card of the registry; every player gets the staffs and copies of the cards and builds them itself, so flow holds no spell (staffs A6a), and builds one world node (room scene, a camera, a player for every player slot that has a device, the fixed wave) that becomes the current scene. It sends `room_entered`, and `room_cleared` when the last enemy of the wave has died. When every player is down it restarts the room after `RESTART_DELAY` (2 seconds): new world, full health, new wave, no shots left, and `Spells.clear()` (every cooldown and build is forgotten; the new players build the start staffs again). A player who leaves and rejoins mid-run gets the start staffs again. The restart also happens when the last enemy dies after everyone is down. If a restart cannot start (content missing) it logs an error and flow goes idle, so Play can start again. Play with the mouse joins the keyboard as P1 only when nobody has joined; anyone already joined (for example a gamepad) plays as they are. A second `play_requested` while a run is on is ignored. `stop_run()` ends the run (tests use it). Mid-run joins and leaves: on `player_joined` a player is added at the room's spawn for joiners of that slot (`RoomBase.joiner_spawns`), else at the player spawn farthest from danger, on `player_left` it is removed (the camera, which `coop` drives, has limits set to the room). Door voting, the room sequence and the run lifecycle arrive in M3, which replaces this slice. `run_started` and `door_vote_requested` are not used yet.
- **The intro (living staffs H6, `intro.gd`):** on a new save (`save`, a `SaveFile`, without the `INTRO_SEEN` flag) `play_requested` shows the intro first (state `INTRO`, the node `Intro` as the current scene; `wants_intro()`, `play_intro(requester)`): one staff dropped per joined player (`drops()`, `drop_time`, `hit_time`), `LENGTH` 14.5 s whatever the number of players. Any joined player's accept, back, pause or staff button skips it at once for everyone (press counts, so no tap is lost); played out or skipped, the save gets `INTRO_SEEN` and the run starts as above. Flow's `step` steps it, so tests drive it with fixed deltas. It plays only for people: `intro_enabled` is false when a test script is the main loop or the game was started with user arguments (`--four-bot`, `--stress`, the timing run); a test switches it on with a save of its own. The sandbox never shows it. `stop_run()` ends an intro too. Its captions are in `intro.gd` until `content/story` has a schema for cutscenes (M3).
- **Waves (M1 slice):** wave 1 is `WAVE` (8 imps); `BUILD_BREAK` (12 s, a fixed build break: nobody's building holds it back or speeds it up; `build_break_started(seconds)` follows `room_cleared`, `build_break_left()` reads it) after each `room_cleared` the next wave stands in the same world with `WAVE_GROWTH` (2) more enemies, up to `WAVE_MAX` (24). Shots in flight are cleared, downed players are revived and protected. `wave_started(wave)` is sent for every wave, including wave 1 right after `room_entered`; `Flow.wave` holds the number. A lost room restarts after `RESTART_DELAY` (1.5 s) at wave 1.
- **Sandbox (staffs B7):** `sandbox_requested` (the main menu's Sandbox button, shown in every build) starts a run in the room `sandbox` (`SANDBOX_ROOM_ID`) instead: no waves and no `wave_started`; the room's dummies stand where its scene's `EnemyStandIn`s are (props W8a/W8c: `training_dummy`, `shooting_dummy`, then more training dummies); `sandbox_changed(true)` follows `room_entered` (every other run start sends `sandbox_changed(false)`, and `stop_run()` of a sandbox too). `sandbox_action_requested(player, action)`: `reset_dummies` frees the dummies and stands fresh ones, `clear_enemies` the arena's enemies (below); anything out of the sandbox is ignored. Killing the arena's enemies sends no `room_cleared` and starts no break. (The old "Imp wave" went with the arena: spawn Cinder Rods there.) When every player is down, after `RESTART_DELAY` they all stand up where they are, protected, with their staffs kept (no restart). Its wizards hold the `dev` staff on all four buttons and start with `sandbox_cards` (`SANDBOX_START_CARDS`) instead of `start_cards` (owner, 2026-11-01): Play's A and X, and two showcase builds of the trigger tree, Y the most shots (`on expire · fire · split ×3 · nova · bolt · frost · split ×3 · nova · bolt`: 216 shots that each fire 216 more, holding the projectile cap (6,000 on desktop) for a few seconds) and B a decoy turret (`timer · on hurt · decoy`: homing fire, frost and lightning bolts every 0.5 s, the lightning one chaining on hit, and a void nova of bolts when it is hurt); `start_cards_for_mode()` picks the list. `Flow.sandbox` (read only: `mode == MODE_SANDBOX`), `dummies()`. **The enemy arena (enemy AI AI8):** `sandbox_spawn_requested(player, enemy_id, count)` and `spawn_in_sandbox(enemy_id, count)` (for tests too) put that many of any registry enemy at the room's enemy spawns, never past WAVE_MAX, only in a sandbox run (returns how many came); `clear_enemies` (`clear_sandbox_enemies()`) takes every spawned enemy away, the dummies stay, and starts no break.
- **The hub (docs/milestones/online-lobby.md, L1):** `hub_requested` (the main menu's Play) starts a run in the room `hub` (`HUB_ROOM_ID`, content/rooms/hub): an island in the void where players join and leave as they like (`player_joined` / `player_left`, at the room's player spawns, with no join protection there), with Play's two staffs (the `dev` staff on RT went in items I2: the hub's rack, I6, replaces it) and start cards, every card in the bag (as the sandbox's; owner, 2026-11-11: to try combos online until a better way to come by cards comes; a run of waves from the stone has Play's bag again), the room's three training dummies (its scene's stand-ins), no wave, and `sandbox_changed(false)`. On a new save the intro plays first, as for `play_requested`. Hits hurt there as anywhere, but a fall costs nothing (owner, 2026-11-13: parties may fight each other and try builds with no consequence): the room's `RoomBase.stand_up_after` (2 seconds) after a wizard is downed it stands up by itself where it fell, at full health and protected for `Downed.JOIN_PROTECTION` (`_stand_up_left`, by seat: state; a teammate's revive, leaving or a new run stops it), and everyone down starts no restart. **The teleporter stone** (a prop of the role `run_start`, stood on where its own area is; props W8c): the hub's rules (`hub`, `HubRules`, gameplay/flow/hub_rules.gd) count the wizards standing on it each tick and whenever one joins or leaves (`standing`, `wizards`: state), `is_stone_lit()` while all of them stand in it, and sends `start_stone_changed(standing, wizards, lit)` when the count differs from what it last sent (`HubRules._stone_sent`, DERIVED: a game whose state a snapshot replaced sends it again); as the hub starts, and (0, 0, false) as it is left. The `run_start` props are asked to enter `lit` or `unlit` with it (`prop_state_requested`; props W8), so the lit look and the `stone_lit` cue are the prop's. **Rooms (props W8c):** a run builds its room's layout once (`RoomBase.build()`) and reads what is where from that instance (`RoomPlaces`); its placements' bodies, props and dummies alike, stand at the run's start in the tree's order (`contents`, `RoomContents`, gameplay/flow/room_contents.gd, which keeps them and answers by kind and role), and a room with the zone `prop_yard` (`ZONE_PROP_YARD`) stands every prop of the registry with no role there (`yard`, `PropYard`), each fresh again `PropYard.RETURN_SECONDS` after it is lit, broken or gone. **Starting:** a seat's A (`accept`) on the lit stone is the command `run_requested` (sent by the HUD's panels, applied at the next tick's start on every machine and in a replay); Flow starts a run of waves (`MODE_WAVES`, `room_id_to_play`) if the stone is lit and that seat has a wizard. A joiner puts the stone out before any command of its tick applies. **Staffs carry over** (owner, 2026-11-10): through the stone and back to the hub, each seat's wizard is made again with the staffs it held, the staffs themselves and their cards (owner, 2026-11-13: a staff equipped in the hub and the cards set on it go into the run as they are; `PlayerController.staff_ids` and `staff_cards`, handed to `start_run` as `heads` and `kept`; `staffs_for_seat`: a button with no id, or one no staff has, holds its mode's, so an empty hand stays empty); a seat that joins mid-run gets its mode's start cards, as anywhere. That run's end (everyone down, after `RESTART_DELAY`) starts the hub again (`_back_to_hub`); a run started by `play_requested` (the tests, the bots, Host/Join until L2) restarts as before. **The altar** (L2): the seats whose wizards stand in `RoomBase.altar` are told as they change (`altar_changed`, a bit each; the HUD's A there asks net/ to open the room, which Flow knows nothing of). **`hub_requested` in the hub starts the hub anew** (net/ begins a recording of it for a machine that joins), **every wizard keeping its staffs:** Flow tells the frames service what a run starting now takes along (`Frames.set_carry_source`, `_carry_now`: in the hub each seat's staffs, anywhere else nothing), a recording begun writes it into its header (`RunCarry`, core/sim), and the hub's start takes it back (`Frames.next_run_carry`), so every machine playing that recording builds the same staffs; during a run of waves it changes nothing. **A seat that joins the hub under way** (a joining machine's player among them) appears beside the altar, at the room's `joiner_spawns` for its seat (online lobby, decision 4; beside it, not on it, so a dash there does not open the room). **No intro under a replay:** a run a replay starts (an online host's among them) never shows it, on a new save either. **Staffs follow the party from the hub into the run and nothing comes back** (owner, 2026-11-10: the hub is the arsenal the right tools for a run are picked from; a run ends lost or won, and back in the hub the party is ready for a new one): the run's end starts the hub with each seat's own staffs, whatever an earlier line here says of staffs kept on the way back. **The return to the hub is a run's start of its own:** Flow ends the run and asks the frames service for `hub_requested` (`Frames.restart`), which sends it as the next step starts; with no frames service (some tests) Flow starts the hub itself.
- **Modes:** `Flow.mode` is the run's mode: `MODE_WAVES` (`&"waves"`, a run of waves), `MODE_SANDBOX` (`&"sandbox"`) or `MODE_HUB` (`&"hub"`); `MODE_WAVES` when idle. `room_id_for_mode()` is the room it starts in, `staffs_for_mode()` the staffs, `restart_delay()` the delay after everyone is down.
- **Room size:** `room_size(room, layout)` (static): at least 640×360, every spawn and door a tile in, and the room scene's `Floor` sprite when it has one. The camera's limits and the projectile bounds (plus `PROJECTILE_MARGIN`) follow it.
- **Known gaps:** no reward, no next room and no way back to the menu (M3); the numbers are constants in `flow.gd`, tuned at C1.
- **Dependency direction:** `core` ← `gameplay` ← `content`. This area may use `core/` and the registry. `core/` never depends on it, and content never reaches into it.
- **Events** (`core/events/events.gd` owns the definitions; this list matches it and the table in [gameplay/README.md](../README.md)):
  - Sends: `room_entered`, `room_cleared`, `wave_started` (and with it `cue_shown` `wave_start`, `WAVE_START_CUE`, on every standing wizard, as its actor; S6, item 13), `build_break_started`, `sandbox_changed`, `start_stone_changed` (and `cue_shown` `stone_lit` at the stone as it lights, as no actor), `door_voted`.
  - Listens to: `enemy_died`, `run_started`, `player_downed`, `player_joined`, `player_left`, and from the HUD `play_requested`, `hub_requested`, `run_requested` (a command), `main_menu_requested` (this machine back to the main menu, not a command: `stop_run`), `sandbox_spawn_requested`, `sandbox_requested`, `sandbox_action_requested` and `door_vote_requested` (`door_voted` is flow's announced result of the vote; `room_entered` follows `play_requested`).
- Areas never call each other directly; they talk through events. [gameplay/README.md](../README.md) has the rules every sub-area shares.

## Review questions

A good PR here changes room order, door voting or transitions, and keeps the no-waiting pillar: one player in the builder never stalls the rest. Besides the general review:

- Does a player idling in the builder block anyone? Does voting work for 1–4 players?
- Does it keep to the dependency direction, without calling another area directly?
