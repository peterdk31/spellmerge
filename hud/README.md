# HUD

## Purpose

Everything the players see and click: panels, the spell builder UI, menus, shared widgets and the one theme. It must stay readable with 4 players on one screen and fully usable with a gamepad.

## Contract

- **Sub-folders:** `panels/` (per-player panels), `builder/` (the radial spell builder), `menus/` (main menu, pause, summary), `widgets/` (shared, reusable controls), `theme/` (the single theme).
- **Events both ways.** The HUD listens to state events from `core/events` and shows only what they say. It also sends player-intent events: requests that carry the player index (0–3), never a finished outcome. It never calls gameplay directly; gameplay checks each request, applies or refuses it, and announces the result as a normal state event (docs/DECISIONS.md, "The HUD sends player-intent events"). Dependency direction: `core` ← `gameplay` ← `content`; the HUD sits beside `gameplay` and uses only `core/`.
- **Events the HUD sends** (`core/events/events.gd` owns the definitions): `hub_requested` (the main menu's Play), `run_requested` (A on the hub's lit stone, `panels.gd`; a command) and `door_vote_requested` (received by `flow`), `staff_change_requested` and `staff_cards_requested` (`player`; the builder), `staff_hand_requested`, `bag_drop_requested` and `bag_use_requested` (`player`; the inventory, items I7, commands), `reward_pick_requested` (`rewards`) and `pause_requested` (`run`) (table in [gameplay/README.md](../gameplay/README.md)). The HUD is the only sender of these events and sends no state events, so each event keeps one sender. Gameplay areas listen to them. Since run generation RG7 also `start_depth_picked` (a seat's pick on its lectern menu, `menus/lectern/`; a command). Since online lobby L2 also `online_open_requested` (A, `accept`, with no menu open, by a player whose wizard stands on the hub's altar, `altar_changed`; `panels.gd`; the lit stone's A comes first), and the main menu's Join online sends `online_join_requested` with a room's code as typed or a machine's code as pasted.
- **Public entry script:** none for the area as a whole; each scene's root script is its own entry (for example a menu scene's script under `menus/`). Other areas never reach into the HUD.
- Widgets build on `core/ui_focus`, so each panel takes input only from its owner (player index 0–3). Nothing assumes a single player, and a player in the builder never makes anyone else wait.
- Use the shared theme; don't style single controls by hand.
- Accessibility: readable text sizes, no information by colour alone, gamepad navigation everywhere.

- **The theme** is `theme/spellmerge_theme.tres`, set as the project theme (`gui/theme/custom`), so every control uses it. Player colours are type variations: `PlayerPanel1-4` (panel border), `PlayerLabel1-4` (text), plus `HealthBar` and `ManaBar`. Add a new look there, not as an override on one control. **The project theme names no file** (no `ext_resource`; `tests/hud/test_title_type.gd` checks it): the engine loads it at its start, before the first import, so on a fresh checkout an imported file it named would not be there yet and the build's import step would fail. A look that needs one is a theme of its own beside it, set on the control that shows it: `theme/title_theme.tres` holds `TitleLabel`, the title type (`art/ui/fonts/title.svg`, a bitmap face drawn for the game) at 32 px, its 2×, white (the glyphs' own Bone light shows as drawn) with an Outline shadow 2 px down and right and no outline, for a boss's name only (docs/STYLE.md, "Font"; docs/milestones/boss-intro.md, rule 7); the boss intro wears it, and everything else under it still finds the project theme. Colours are from `docs/STYLE.md`.
- **The panels** (`panels/`): `panels.tscn` is the autoload `Hud`, a `CanvasLayer` with one `player_panel/` per player in a corner (P1 top left, P2 top right, P3 bottom left, P4 bottom right; kept small (owner, 2026-11-19): about 96 px wide and 19 px tall plus 15 px per staff row (at most about 80 px; 8 px more for a seat played on another machine, which says ONLINE; the room the old HP and MP bars took is kept for the run's coins and relics, M3), so four fit a 640×360 view; the background is 60% translucent so a player or enemy under a corner panel still shows). ## The words for playing online

`widgets/online_words.gd` is the one place playing online is worded (online lobby L5b). Whatever links the machines says why something failed or ended as a name with a few facts (`OnlineWhy`, `core/events/online_why.gd`; `online_changed`'s `reason` and `facts`), never as a sentence; the main menu's online box and the online line (`widgets/online_line.gd`) both ask `OnlineWords.said`, and the line asks `OnlineWords.line` for the facts of `online_line_changed` (an open room's code, who is in, catching up, parted) before the counters. The online line also says, in the hub, why a room could not be opened or a machine was turned away: no menu is open there to say it. A name with no words still says "It did not work.", and a fact that is missing or of another kind is worded as nothing. A new name in `OnlineWhy` needs its sentence here: `tests/hud/test_online_words.gd` fails for one without. A seat played on another machine says ONLINE on its corner panel while this machine plays with others (online lobby L5c; `PlayerPanel.set_online`, asked of `core/input` by `panels.gd` each frame). The room's code over the hub's altar is Feel's, not the HUD's (`gameplay/feel/altar_code.gd`).

## Allowed files

`.gd`, `.tscn`, `.tres`, UI art (`.png`, `.svg`), plus `.uid`, `.import` and `.license` files. Limits: 1 MB per image, 1 MB for anything else. Typed GDScript only; no banned APIs. Tests for the HUD go in `tests/hud/`; the runner and naming are documented in `tests/README.md`, which a later task writes.

## Steps

1. Reuse widgets from `widgets/` before adding new ones.
2. Add UI art lines to `art/manifest.json`.
3. Run the checks below, then open a PR using the template, with a screenshot or short GIF.
