# HUD

## Purpose

Everything the players see and click: panels, the spell builder UI, menus, shared widgets and the one theme. It must stay readable with 4 players on one screen and fully usable with a gamepad.

**Opens for PRs in M4** (Polish and variety; see "Opens for PRs" in docs/ROADMAP.md). Until then Claude builds it.

## Contract

- **Sub-folders:** `panels/` (per-player panels), `builder/` (the spell builder), `menus/` (main menu, pause, summary), `widgets/` (shared, reusable controls), `theme/` (the single theme).
- **Events both ways.** The HUD listens to state events from `core/events` and shows only what they say. It also sends player-intent events: requests that carry the player index (0–3), never a finished outcome. It never calls gameplay directly; gameplay checks each request, applies or refuses it, and announces the result as a normal state event (docs/DECISIONS.md, "The HUD sends player-intent events"). Dependency direction: `core` ← `gameplay` ← `content`; the HUD sits beside `gameplay` and uses only `core/`.
- **Events the HUD sends** (`core/events/events.gd` owns the definitions): `play_requested` and `door_vote_requested` (received by `flow`), `build_change_requested` and `spell_swap_requested` (`player`), `reward_pick_requested` (`rewards`) and `pause_requested` (`run`) (table in [gameplay/README.md](../gameplay/README.md)). The HUD is the only sender of these events and sends no state events, so each event keeps one sender. Gameplay areas listen to them.
- **Public entry script:** none for the area as a whole; each scene's root script is its own entry (for example a menu scene's script under `menus/`). Other areas never reach into the HUD.
- Widgets build on `core/ui_focus`, so each panel takes input only from its owner (player index 0–3). Nothing assumes a single player, and a player in the builder never makes anyone else wait.
- Use the shared theme; don't style single controls by hand.
- Accessibility: readable text sizes, no information by colour alone, gamepad navigation everywhere.

- **The theme** is `theme/spellmerge_theme.tres`, set as the project theme (`gui/theme/custom`), so every control uses it. Player colours are type variations: `PlayerPanel1-4` (panel border), `PlayerLabel1-4` (text), plus `HealthBar` and `ManaBar`. Add a new look there, not as an override on one control. Colours are from `docs/STYLE.md`.
- **The panels** (`panels/`): `panels.tscn` is the autoload `Hud`, a `CanvasLayer` with one `player_panel/` per player in a corner (P1 top left, P2 top right, P3 bottom left, P4 bottom right; about 112×55 px each, so four fit a 640×360 view; the background is 60% translucent so a wizard or enemy under a corner panel still shows). It hears `player_joined`, `player_left`, `room_entered`, `player_stats_changed` (from `player`) and `UIFocus.opened`/`closed`, and shows only that. A panel shows for a joined player after the first room; it takes no input. It says "P1".."P4", "HP", "MP" with numbers, "DOWN" at 0 health and "MENU" while that player's overlay is open (priority DOWN), so nothing is shown by colour alone.
- **The overlay** (`panels/overlay/`): a small per-player menu under (P1, P2) or over (P3, P4) that player's corner panel (nodes `Root/Overlay1-4` of `panels.tscn`). `panels.gd` toggles it when its owner presses the `overlay` action (read from `core/input` press counts, so a quick tap is not lost; a slot with no device is ignored). Opening goes through `UIFocus.open`, so only the owner's device moves (up/left, down/right), activates (`cast`) or goes back (`dodge`), the owner's wizard stands still and the other three players carry on. It never pauses the game, and it closes when the owner closes it, when the device leaves, or when another request replaces it. Controls: "Resume", "Build" (sends only the node's own signal `build_pressed(player)`; `panels.gd` then opens that player's builder, the quick view during a wave) and "Drop component" (M2 part 18: the quick action that works in combat; it replaces the three buttons with a two-column list of the bag components that fit a free slot of the active spell and sends `build_change_requested`; greyed when nothing fits; `dodge` leaves the list, then closes the overlay). The focused control is marked with "> ", not by colour alone. While it is open the corner panel shows "MENU".
- **The hurt vignette** (`panels/vignette/`, node `Root/Vignette` of `panels.tscn`, created by `panels.gd`): a red glow at the screen edges, strongest toward the corner of the wizard whose health fell, fading in half a second. It comes only from a drop in the health of `player_stats_changed`, takes no input and never covers the panels. A hit adds glow by the share of maximum health it took, and less the more wizards are playing (divided by the square root of their number), so a four-player fight does not keep the screen red; the middle of the screen stays clear. The setting `Hud.get_vignette().enabled = false` turns it off (kept in memory, like `Feel.shake_enabled`; saving it waits for `core/save` and the settings screen).
- **Swap** (M2 part 18): the corner panel shows "Spell A" or "Spell B" from `active_spell_changed(player, slot)`. `panels.gd` turns a press of `swap` (from the press counter of `core/input`) into `spell_swap_requested(player)`; presses are dropped while that player is in a menu, down, not joined or outside a room. `player` decides and answers with `active_spell_changed`.
- **The wave line:** a "Wave N" label (`Root/WaveLabel`, top middle, no input) set from `wave_started` and hidden when a run starts or ends.
- **The build break line** (M2 part 19; `Root/BreakRow`, top middle under the wave line, drawn over the builders, no input): a code-drawn hammer (`widgets/hammer_icon.gd`) and "Build N" (seconds left, rounded up). It shows from `build_break_started(seconds)` and counts down from `_process` (`step_break(delta)`); it is display only, so `Flow` alone decides when the wave starts. Limit: the HUD only knows the break from the event, so a player or HUD that joins mid-break shows no break line until the next one. `wave_started` and a run starting or ending hide it.
- **The spell builder** (`builder/`, M2 part 16; nodes `Root/Builder1-4` of `panels.tscn`): the corner panel expanded toward the middle. It sits beside its player's corner panel (to the right of P1 and P3, to the left of P2 and P4, about 200×170 px), so four open builders and four corner panels fit 640×360 without covering one another or leaving their quarter of the screen. Left column: the title ("P1 Spell A", plus "held N" below the first level), the spell tabs `A` and `B` and `Close`, the six slots of the chain (form, element, three modifiers, trigger; a modifier slot opens only in the first free place, as `player` fills them), and `< Up` and `Held >` (the spell a trigger holds, at most two levels down). Right column: the bag rows for the selected slot only (components of the slot's kind, a "None" row for a filled slot except the form, the current component marked with " *"). Opened from the overlay's "Build" (it takes the overlay's place in `core/ui_focus`) and closed by `Close`, by `dodge` anywhere but on a bag row (there it goes back to the slot), by the `overlay` action, when its owner goes down or when the run ends. Activating a slot moves focus to the first bag row; activating a row sends `build_change_requested(player, path, slot, id)` with the path `[spell, 0, ...]` (one 0 per held level). It never changes what it shows by itself: the picture follows `recipe_changed(player, slot, recipe)` and `bag_changed(player, ids)` from `player`, so a refused change leaves it as it was. Names, icons and kinds come from `Spells.component_name`, `component_icon` and `component_kind`, since the HUD never reads a component's fields. Buttons use the `BuilderButton` theme variation (10 px). The mouse does nothing yet. **The info panel** (M2 part 17; `Info`, a top-level child of each builder, 112×112 px, in the free strip of the player's quarter: under the corner panel for P1/P2, over it for P3/P4, at the screen edge) shows, from `Spells.builder_view` for the spell and held level shown: "Complexity N/12" in words with a bar (the whole spell, held spells included; `ComplexityBar` variation), "Dmg", "Shots" ("Ray" for a beam), "Cool" and "Mana", and a code-drawn mini-preview of the shot pattern (`spell_preview.gd`: fan, ring, orbit circle, rune dot, ray; in the element's tint). Below it one text line: "Refused: <reason>" after a `build_refused` for this player (cleared by the next request or change), else the one-line description of the component in focus (`Spells.component_description`, empty until part 23). It is words, never colour alone. **The quick view** (M2 part 18): `panels.gd` calls `set_quick(true)` on every builder at `wave_started` and `set_quick(false)` at `room_cleared`, `run_started` and `run_ended`. An open builder folds (one opened during a wave starts folded): it follows the active spell (`active_spell_changed`), shows its slot chain read only, hides the tabs, held levels, bag and info panel, and has "Drop component" and "Close". "Drop component" lists the bag components that fit the empty element slot or the first free modifier slot (`widgets/drop_choices.gd`; no icons, tighter rows so the longest list of ten fits the quarter); activating one sends `build_change_requested(player, [active], slot, id)`; `dodge` leaves the list, then closes. Choices are kept (they live in the player's recipes) and the full builder is back after the wave. The bag rows are made once from the biggest group of one kind; a bag that grows while a builder is open shows the new rows from the next opening.
- Events the HUD listens to: `player_joined`, `player_left`, `room_entered`, `wave_started`, `build_break_started`, `player_stats_changed`, `run_started`, `run_ended`, `recipe_changed`, `bag_changed`, `build_refused` (the builders), `active_spell_changed` (the panels, builders and overlays), `room_cleared` (ends the quick view) and `UIFocus` signals. Events it sends: `build_change_requested` (the builders and overlays) and `spell_swap_requested` (`panels.gd`).

## Allowed files

`.gd`, `.tscn`, `.tres`, UI art (`.png`, `.svg`), plus `.uid`, `.import` and `.license` files. Limits: 1 MB per image, 1 MB for anything else. Typed GDScript only; no banned APIs. Tests for the HUD go in `tests/hud/`; the runner and naming are documented in `tests/README.md`, which a later task writes.

## Steps

1. Pick an issue labelled `now` in this area (once open) and comment `/claim`.
2. Reuse widgets from `widgets/` before adding new ones.
3. Add UI art lines to `art/manifest.json`.
4. Run the checks below, then open a PR using the template, with a screenshot or short GIF.

## Example to copy

`hud/menus/main_menu/main_menu.tscn` and `main_menu.gd`: the main menu with the Play button. Play sends `play_requested(0)` through the `Events` autoload and nothing else: it never calls `flow` and never changes the scene (flow does, on the event). The test is in `tests/gameplay/flow/test_flow.gd` (it presses the button and scans the script). For a panel, copy `hud/panels/player_panel/` (`player_panel.tscn` and `.gd`: the root script gets its numbers through methods, listens to nothing, and styles itself only through theme variations); its container is `hud/panels/panels.gd`, and the tests are `tests/hud/test_panels.gd` and `tests/gameplay/player/test_player_stats.gd`. For the builder, copy `hud/builder/` (tests in `tests/hud/test_builder.gd`, a suite test with real wizards and four builders open at once; `tests/screenshots/shot_builder.gd` shows it). For the overlay, copy `hud/panels/overlay/` (it answers only the signals that name its own player index); its test is `tests/hud/test_overlay.gd` (with one overlay open the other three players still move).

## Rating questions

Besides the standard criteria:

- Is it readable with 4 players at 1× on a small screen?
- Can it be fully used with a gamepad, and does each panel respond only to its owner?
- Does it reuse the shared theme and widgets?
