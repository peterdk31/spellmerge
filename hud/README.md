# HUD

## Purpose

Everything the players see and click: panels, the spell builder UI, menus, shared widgets and the one theme. It must stay readable with 4 players on one screen and fully usable with a gamepad.

## Contract

- **Sub-folders:** `panels/` (per-player panels), `builder/` (the spell builder), `menus/` (main menu, pause, summary), `widgets/` (shared, reusable controls), `theme/` (the single theme).
- **Events both ways.** The HUD listens to state events from `core/events` and shows only what they say. It also sends player-intent events: requests that carry the player index (0–3), never a finished outcome. It never calls gameplay directly; gameplay checks each request, applies or refuses it, and announces the result as a normal state event (docs/DECISIONS.md, "The HUD sends player-intent events"). Dependency direction: `core` ← `gameplay` ← `content`; the HUD sits beside `gameplay` and uses only `core/`.
- **Events the HUD sends** (`core/events/events.gd` owns the definitions): `play_requested` and `door_vote_requested` (received by `flow`), `staff_change_requested` (`player`), `reward_pick_requested` (`rewards`) and `pause_requested` (`run`) (table in [gameplay/README.md](../gameplay/README.md)). The HUD is the only sender of these events and sends no state events, so each event keeps one sender. Gameplay areas listen to them.
- **Public entry script:** none for the area as a whole; each scene's root script is its own entry (for example a menu scene's script under `menus/`). Other areas never reach into the HUD.
- Widgets build on `core/ui_focus`, so each panel takes input only from its owner (player index 0–3). Nothing assumes a single player, and a player in the builder never makes anyone else wait.
- Use the shared theme; don't style single controls by hand.
- Accessibility: readable text sizes, no information by colour alone, gamepad navigation everywhere.

- **The theme** is `theme/spellmerge_theme.tres`, set as the project theme (`gui/theme/custom`), so every control uses it. Player colours are type variations: `PlayerPanel1-4` (panel border), `PlayerLabel1-4` (text), plus `HealthBar` and `ManaBar`. Add a new look there, not as an override on one control. Colours are from `docs/STYLE.md`.
- **The panels** (`panels/`): `panels.tscn` is the autoload `Hud`, a `CanvasLayer` with one `player_panel/` per player in a corner (P1 top left, P2 top right, P3 bottom left, P4 bottom right; about 112×55 px each, so four fit a 640×360 view; the background is 60% translucent so a wizard or enemy under a corner panel still shows). It hears `player_joined`, `player_left`, `room_entered`, `player_stats_changed` (from `player`) and `UIFocus.opened`/`closed`, and shows only that. A panel shows for a joined player after the first room; it takes no input. It says "P1".."P4", "HP", "MP" with numbers, "DOWN" at 0 health and "MENU" while that player's overlay is open (priority DOWN), so nothing is shown by colour alone.
- **The overlay** (`panels/overlay/`): a small per-player menu under (P1, P2) or over (P3, P4) that player's corner panel (nodes `Root/Overlay1-4` of `panels.tscn`). `panels.gd` toggles it when its owner presses the `overlay` action (Start, Tab or E; read from `core/input` press counts, so a quick tap is not lost; a slot with no device is ignored). Opening goes through `UIFocus.open`, so only the owner's device moves (up/left, down/right), activates (`cast_a`) or goes back (`cast_b`), the owner's wizard stands still and the other three players carry on. It never pauses the game, and it closes when the owner closes it, when the device leaves, or when another request replaces it. Controls: "Resume" and "Build" (sends only the node's own signal `build_pressed(player)`; `panels.gd` then opens that player's builder). There is no quick "Bag" drop: the full builder is open at any time, waves included (owner, staffs A6a). The focused control is marked with "> ", not by colour alone. While it is open the corner panel shows "MENU".
- **The hurt vignette** (`panels/vignette/`, node `Root/Vignette` of `panels.tscn`, created by `panels.gd`): a red glow at the screen edges, strongest toward the corner of the wizard whose health fell, fading in half a second. It comes only from a drop in the health of `player_stats_changed`, takes no input and never covers the panels. A hit adds glow by the share of maximum health it took, and less the more wizards are playing (divided by the square root of their number), so a four-player fight does not keep the screen red; the middle of the screen stays clear. The setting `Hud.get_vignette().enabled = false` turns it off (kept in memory, like `Feel.shake_enabled`; saving it waits for `core/save` and the settings screen).
- **The staff word** (staffs A6a): the corner panel shows "Staff X" for the staff the player cast last (from `staff_cast`), nothing before the first cast. There is no swap: every staff has its own button.
- **The wave line:** a "Wave N" label (`Root/Strip/WaveLabel`, 12 px, in the middle of the view left of the break line, no input) set from `wave_started` and shown only while a wave is on: hidden at `room_cleared` (so not during the build break) and when a run starts or ends.
- **The build break line** (M2 part 19; `Root/Strip/BreakRow`, right of the wave line in the same strip, no input): a code-drawn hammer (`widgets/hammer_icon.gd`) and "Build N" (seconds left, rounded up). It shows from `build_break_started(seconds)` and counts down from `_process` (`step_break(delta)`); it is display only, so `Flow` alone decides when the wave starts. Limit: the HUD only knows the break from the event, so a player or HUD that joins mid-break shows no break line until the next one. `wave_started` and a run starting or ending hide it.
- **The staff builder** (`builder/`, staffs A6a and B8; nodes `Root/Builder1-4` of `panels.tscn`): the corner panel expanded toward the middle, beside its player's corner panel (to the right of P1 and P3, to the left of P2 and P4), so four open builders and four corner panels fit 640×360 without covering one another. The title ("P1 Staff X"), the four staff tabs named by their buttons (`A`, `X`, `Y`, `B`) and `Close`, then two lists in scrolling windows (`widgets/row_window.gd`, 8 rows at a time, 8 px text): the slots of the shown staff ("3 Fire >5" for a card that goes into the carrier in slot 5, "> you" on the caster, "> aim" at the aim point; "5 Bolt #1" for a carrier and its cast; "4 -" for an empty slot; " !" after a card that does nothing where it is; "^" before a card picked up; " <" after the cards linked to the focused one) and the bag ("Empty", then every card, the one in the selected slot marked " *"). Opened from the overlay's "Build" at any time, waves included, and closed by `Close`, by `cast_b` anywhere but on a bag row (there it goes back to the slot), by the `overlay` action, when its owner goes down or when the run ends. The d-pad moves in two dimensions through a navigator given to `core/ui_focus` (tabs in a row, up from a list to the tabs, left and right between the slots and the bag), so every slot is reached with the d-pad alone; LB and RB (`page_prev`, `page_next`) show the previous or next staff. **Pick and place:** `cast_a` on a slot with a card picks it up, `cast_a` on another slot (of any staff) places it, swapping, with `card_move_requested(player, from staff, from slot, to staff, to slot)`; `cast_a` on the bag while holding, or `cast_x` on a slot, sends the card back to the bag (to staff -1); `cast_b` drops it where it was. With nothing held, activating an empty slot selects it and moves focus to the bag, and activating a bag card sends `staff_change_requested(player, staff, slot, id)` and selects the next slot, so a staff is still built left to right by picking cards one after another. **Player 1's mouse:** a click works as `cast_a`, a drag from a slot to a slot (or to the bag), or from the bag to a slot, moves the card (only builder 1's buttons take the mouse). It never changes what it shows by itself: the picture follows `staff_changed(player, staff, plan)` (the plain `Spells.staff_view`: `cards`, `casts`, `wasted`) and `bag_changed` from `player`. **The info panel** (`Info`, a top-level child, 112×112 px, in the free strip of the player's quarter) shows the cast plan (one line per cast of the staff's cycle, from the plan, its words then its damage if every shot lands once, the plan's `damage`) and a note: "Refused: <reason>" after a `build_refused`, else "Does nothing: <reason>" for a wasted card in the focused slot, else where the focused card goes ("Goes into Bolt (slot 2).") and its description (`Spells.component_description`); its last line is a hint for the focused control (`widgets/hint_line.gd`: the glyph of the button, then the verb). **Show buttons, not action names** (owner, #4): use `widgets/action_glyph.gd`, never the words "Cast" or "Dash". Buttons use the `BuilderButton` theme variation; the one in focus takes `BuilderButtonFocus` besides the "> " mark.
- Events the HUD listens to: `player_joined`, `player_left`, `room_entered`, `wave_started`, `build_break_started`, `player_stats_changed`, `run_started`, `run_ended`, `staff_changed`, `bag_changed`, `build_refused` (the builders), `staff_cast` (the corner panel shows the staff cast last), `room_cleared` and `UIFocus` signals. Events it sends: `staff_change_requested` and `card_move_requested` (the builders).

## Allowed files

`.gd`, `.tscn`, `.tres`, UI art (`.png`, `.svg`), plus `.uid`, `.import` and `.license` files. Limits: 1 MB per image, 1 MB for anything else. Typed GDScript only; no banned APIs. Tests for the HUD go in `tests/hud/`; the runner and naming are documented in `tests/README.md`, which a later task writes.

## Steps

1. Reuse widgets from `widgets/` before adding new ones.
2. Add UI art lines to `art/manifest.json`.
3. Run the checks below, then open a PR using the template, with a screenshot or short GIF.

## Example to copy

`hud/menus/main_menu/main_menu.tscn` and `main_menu.gd`: the main menu with the Play button. Play sends `play_requested(0)` through the `Events` autoload and nothing else: it never calls `flow` and never changes the scene (flow does, on the event). The test is in `tests/gameplay/flow/test_flow.gd` (it presses the button and scans the script). For a panel, copy `hud/panels/player_panel/` (`player_panel.tscn` and `.gd`: the root script gets its numbers through methods, listens to nothing, and styles itself only through theme variations); its container is `hud/panels/panels.gd`, and the tests are `tests/hud/test_panels.gd` and `tests/gameplay/player/test_player_stats.gd`. For the builder, copy `hud/builder/` (tests in `tests/hud/test_builder.gd`, a suite test with real wizards and four builders open at once; `tests/screenshots/shot_builder.gd` shows it). For the overlay, copy `hud/panels/overlay/` (it answers only the signals that name its own player index); its test is `tests/hud/test_overlay.gd` (with one overlay open the other three players still move).

## Validate

```sh
tools/check.sh
ci/build/build.sh --quick --tests
```

## Review questions

Besides the general review:

- Is it readable with 4 players at 1× on a small screen?
- Can it be fully used with a gamepad, and does each panel respond only to its owner?
- Does it reuse the shared theme and widgets?
