# Net

## Purpose

Two machines playing one run (the netcode spike, [docs/milestones/netcode-spike.md](../docs/milestones/netcode-spike.md); several players a machine, and joining through a room, since the online lobby's L2, [docs/milestones/online-lobby.md](../docs/milestones/online-lobby.md)): host-ordered lockstep, built on the replay machinery of `core/sim`. The host records its run and sends every tick's input frames; the client plays them as a live replay and sends its own seats' frames. Only inputs cross the wire, and the simulation is the same on both machines.

**Nothing outside this folder knows a network exists.** The game sees input frames (`core/sim/frames.gd`), whatever made them: a device, a bot, a replay, or a session here. This folder knows `core/sim` and `core/input`, and nothing of gameplay or the HUD.

This is the one folder whose scripts may name networking classes (the owner's exception to hard rule 4, 2026-11-10, docs/DECISIONS.md; `NET_DIR` in `ci/smbot/rules.py`), and only a WebRTC peer, its data channel, and the WebSocket to the room server. It is Claude's and the owner's only. Only `NetRtc` and `NetRtcLink` name the WebRTC classes and only `NetSignalSocket` the WebSocket, and nothing connects anywhere until a player presses Host or Join.

## What is here

| File | What it is |
|---|---|
| `net_message.gd` (`NetMessage`) | The messages on the wire and their strict decoder: HEADER, TICK, FRAME, HASHES, PARTED, PING, PONG, SEAT_ASK, LOBBY, RUN |
| `net_link.gd` (`NetLink`) | What a session knows of the wire: whole messages out and in, in order, open or closed |
| `net_loopback.gd` (`NetLoopback`) | A link inside one process (the tests, the measured grid) |
| `net_conditioner.gd` (`NetConditioner`) | A link made worse on purpose: delay, jitter and loss, seeded, on a clock it is given |
| `net_session.gd` (`NetSession`) | What one link's session is: reading the link within a limit, refusing it (`problem`), the checks, the parting kept, the counters |
| `net_host.gd` (`NetHost`) | The host's side: the recording and up to three guest machines, each joined to the run from its first tick or a while in; gives each seat of a guest's a `FrameSource`, sends the header and every recorded tick to each, hashes the state once and keeps its checks for theirs |
| `net_guest.gd` (`NetGuest`) | One guest machine as the host sees it (a `NetSession`): its link, the seats it asked for and was given, the frames it sent for them, its own limits, its checks compared, its counters |
| `net_client.gd` (`NetClient`) | A guest machine's session: gives the frames service a `LiveFeed` that plays the host's run, has its devices seated where the host says, sends a frame for each of its seats every step, and catches up on a run joined a while in |
| `net_delay.gd` (`NetDelay`) | The client's input delay `D`: given, or following the ping (the middle one of the last five; up at once, down slowly). Knows no link or session |
| `net_checks.gd` (`NetChecks`) | The hash checks: one part of the state each tick, a whole check every 60 |
| `net_stats.gd` (`NetStats`) | A session's counters (ping, delay, late frames, waits, bytes, check and link time) |
| `net_webrtc.gd` (`NetWebRTC`) | Whether this build has WebRTC: a browser's own, or the WebRTC extension that `ci/build/webrtc.sh` puts in the desktop builds and the test runs (S3; `addons/webrtc_native/`, never committed). A peer made without it logs an engine error, so ask first |
| `net_code.gd` (`NetCode`) | The code two players swap by copy and paste: a session description and its candidates as text, and the strict check of a pasted one |
| `net_handshake.gd` (`NetHandshake`) | How two machines come to hold a link: the host offers, each takes the other's code, and a `NetLink` is there. What `NetPlay` knows of connecting |
| `net_rtc.gd` (`NetRtc`) | The handshake over WebRTC: the peer, its channel, the one STUN server, a relay (TURN) when the room server hands one over, the code once the candidates are gathered; a link never made says why as far as the two codes tell (`why_no_link`: a relay that did not help, one network, a machine with no address from outside, or two networks only a relay gets through), with no address named |
| `net_relay.gd` (`NetRelay`) | A relay as plain data (addresses, user name, password): what crosses from whoever hands relays out to whoever links, so neither knows the other's form |
| `net_rtc_link.gd` (`NetRtcLink`) | The link over the WebRTC data channel: polled when read, large messages split and joined |
| `net_signal.gd` (`NetSignal`) | What the game and the room server (`server/signal/`) say to each other: the server's messages read strictly, the game's written, a room code's form, and the server's one address (`URL`) |
| `net_signal_socket.gd` (`NetSignalSocket`) | The WebSocket to the room server: whole text messages, polled when read |
| `net_signal_handshake.gd` (`NetSignalHandshake`) | The handshake through the room server: a room's five characters in place of two pasted codes. An inner handshake (`NetRtc`) for each other machine still makes and checks the codes and the link |
| `net_play.gd` (the autoload `NetPlay`) | Playing online: hears the requests on the bus (the menu's Host and Join, the hub's altar), chooses the handshake (the one place), has both machines load, makes the session, starts or joins the run, follows the Tick, says where things stand, saves a parted run |
| `net_log.gd` (`NetLog`) | A session's counters as a file, `user://net/host.log` or `client.log` |
| `net_press_probe.gd` (`NetPressProbe`) | Times the client's presses from the step they were sent to the step they ran (a measure for S5; it changes nothing) |

The seams, each one-way: a session knows a `NetLink` (never what carries it), and reaches the game only through three things of `core/sim` and `core/input`: the frames service (`Frames.record`, `set_source`, `play_live`), the input layer (the host: a virtual device for each of the client's seats; the client: `join_asker` and `join_as`, by which the host seats its devices), and a `Callable` that hands it the game's areas for the checks. The frames service holds the host's `FrameSource` and the client's `LiveFeed` (small inner classes that call their session) and knows nothing of sessions.

Connecting has its own seams. `NetPlay` knows a `NetHandshake` (never WebRTC) and the two sessions; a handshake hands it a `NetLink`. It reaches the rest of the game only through `core/`: the bus (the `online_*` requests in; `online_changed` and `online_line_changed` out; `play_load_requested` to whoever loads; `loading_started` and `loading_finished`; and `hub_changed`, which says whether the party is in the hub, where a machine may join), the input layer through the sessions, the Tick's `ticked` and `state_areas`, and the frames service (`record` for a room's hub, and through the sessions). The main menu and the HUD's line know the bus only.

**How machines find each other stays behind `NetHandshake`.** By hand (`NetRtc`) and through the room server (`NetSignalHandshake`) are two of them; a platform's own lobbies and relay would be another handshake and another `NetLink` beside these, with nothing else changed. So nothing outside `net_signal*.gd` knows a room server, a room code's form or its address, and nothing outside `net_rtc*.gd` and `net_code.gd` knows WebRTC. A host that takes several machines asks any handshake for `next_link()`.

## Host and Join

1. **Host** makes this machine's code (`online_changed(&"code", code, "")`); the player sends it to the other, by chat.
2. **Join**, with the host's code pasted, makes that machine's code, which goes back the same way.
3. **The host given that code**, the machines look for each other (a public STUN server tells each its address as the internet sees it; on one network or one machine none is needed).
4. **Linked**, each machine loads what a room needs (`play_load_requested`), then the client pings; the host starts the run, a sandbox, when it is loaded and has heard three pings.
5. **While it plays**, one line of counters goes to the HUD a second and a row to the log every ten; a failed hash check is said once and each side saves its run (`user://replays/online_host_parted.replay`, `online_client_parted.replay`).
6. **The other machine gone:** the host's run plays on without the client's seat; the client's replay ends and its game goes on alone. All four seats are the machine's again, its own device staying where it plays. Nothing more is heard after that: no second run starts under one still playing.

## A room: the hub's altar and Join online

1. **A wizard of the host's presses A on the hub's altar** (`online_open_requested`, from the HUD): the room server is asked for a room, and its code is said (`online_changed(&"code", code, "")`, and in the HUD's line). The party plays on as it was: nothing is recorded and no seat changes until a machine joins. A again says the code again (A is also the dash, so it never closes the room; the room closes with the game, or by the server after fifteen minutes with no join).
2. **Another machine types the code** under the main menu's Join online (`online_join_requested`; what starts as a machine's code does is joined by hand instead). The handshake links the two.
3. **Linked**, each loads what a room needs, the joining machine has its devices asked for, and pings. The host, hearing it ready, begins a recording of its hub (`Frames.record(&"hub_requested", ...)`: the hub starts anew, everyone back at their spawn with their mode's staffs) unless it records one already that is not too long (`MAX_CATCH_UP`), and joins the machine to it (`NetHost.begin`).
4. **The joining machine plays the recording from its first tick** until it has caught up (many ticks a step, `NetClient.pace`), then on, live. Its wizards come at the tick the host seated them, on every machine.
5. **From the hub into a run** (the stone) is the game's own doing, inside that recording. **Back in the hub after a run, a new recording begins:** Flow asks the frames service for the hub's start (`Frames.restart`), which sends it between ticks and records anew (`recorded_anew`); the host sends every guest machine the new header and its ticks from the first (`NetHost.rebegin`). A guest plays the recording before to its end (its own game asked for the same start at that tick, and waits), then the new one, and says so (RUN). What it sent before that is of the recording before, and dropped. So a recording is never longer than one visit to the hub and the run from it.
6. **A machine that comes while the party is out of the hub** (`hub_changed` says where it is) is turned away before anything of its is read (it is given no seat, even for a moment), and told. Joining is in the hub only.
7. **A machine gone:** its seats leave and the others play on. With the last one gone the room stays open for the next (who joins a hub begun anew), and the recording ends. **The room closed** under a run (its fifteen minutes, the server): the run plays on, and nobody else joins.
8. **Back to the main menu** (the pause menu's "Main menu", `main_menu_requested`; the frames service, Flow and the HUD hear it too, each for its own part): `NetPlay` lets go of everything at once in any phase (OFF). A guest's link closes, so the host lets its seats go at once (not after the silence below); a host's guests see it gone and its room closes. From the menu the machine may host or join again, with no restart of the game: a machine whose host left joins another room this way.

**A party takes up to three guest machines** (`NetHost.GUESTS`; L3): each is its own `NetGuest`, joined to the hub's recording when it is ready while the others play on; a link past the third is closed. A machine that joins a recording others already play catches up on it from its first tick (it cannot begin anew under them; it is one visit to the hub and the run from it, no more). By hand (Host and Join by code) it is one guest machine.

## Seats

**How machines meet and what they play are kept apart.** `NetPlay` picks a handshake by the way in (`_handshake_for`: by hand, through a room) and never reads a code: each handshake says whether a typed text is its own (`NetHandshake.takes`). What is played (a party's hub that machines come to and go from, or one run two machines start together) is the request's, not the handshake's, so another way in (a platform's lobbies) opens the same party.

**Seats are the host's to give.** The host's own players take seats as they always do (the lowest free). A joining machine's devices are not seated by its own input layer (`join_asker`): each is given a number of that machine's (0 to 3, never a device id) and asked for (SEAT_ASK). The host gives the lowest seat nobody holds, by joining a virtual device there through its input layer, so the frames service seats it and the recording says so at one tick for every machine. **A seat is only given between ticks** (an ask read while a tick's frames are built waits for the tick's end), as a pad joins between ticks: given in the middle, a seat whose frame of that tick is built already would be seated on the host a tick before the recording, and so every other machine, says so. Every ask is answered with the LOBBY: which of that machine's players holds which seat, and how many asks were answered (one given no seat may ask again). The joining machine seats each device where the lobby says (`join_as`), as soon as the seat is free in the run as it plays it; a seat is that machine's (`LiveFeed.local_seats`) while its device sits on it. A player who leaves says so in its seat's frame (LEAVE); the host takes the seat back and says so in the next lobby. By hand (Host and Join by code), the host gives the other machine's first player seat `NetHost.SEAT` beforehand, so both start with a seat.

**A run two machines start together cannot load at its start** (a load takes each its own time; they would begin on different ticks and part), which is why step 4 loads first.

## How a run goes

1. **Before the run** the host takes each guest machine's link with the seats it plays (`NetHost.add_guest(link, seats)`: up to three machines, any of seats 1 to 3, none given twice), and each side calls `pump()` every physics step. The clients ping; the host answers each.
2. **`NetHost.start(start, starter)`** joins a virtual device on each guest's seats through the input layer (so the frames service seats them and the recording knows), makes each such seat's source its guest's, starts the run recorded (`Frames.record`) and sends its header to every guest.
3. **A client takes the header** only if it is of this build and this content; anything else closes the link (`problem`). Which seats are its own is the lobby's to say, not the header's. It works out its input delay `D` (given, or the measured round trip in ticks, the cushion and one) and starts the live replay (`Frames.play_live`). A `D` that was not given follows the ping through the run (`NetDelay`): the middle one of the last five pings, up as soon as that asks for more, down only by two ticks or more and then a tick every four frames. The client never sends a frame for an earlier host tick than the one before (the host refuses that). From here the frames service drives both sessions; neither has a `_process` or a thread.
4. **Every tick on the host:** the frames service asks the host for each guest seat's frame. That seat's guest reads its link (once a tick) and uses up every frame of that seat that is for this tick or an earlier one: the walk, aim and held buttons are the newest's; the presses and commands are all of theirs. **With none arrived, the last frame stands in without its presses and commands**, and the late frame's come with the next tick. The host never waits. After the tick, `after_tick()` sends it.
5. **Every physics step on the client:** `pump` adds the ticks that arrived to the replay, `send` sends each of its seats' frames (a FRAME each, all for one host tick) for the host's tick `tick + D`, and the frames service runs the ticks the feed paces (none while none is there, up to three to catch up).
6. **The checks:** after every tick every machine hashes one part of the state (`SimHash.slice`, part `tick % 60`); every 60 ticks each client sends its hashes and the host compares them with its own of that tick (hashed once, kept for every guest). Where they differ, that guest keeps the tick and the areas (`parted_tick`, `parted_areas`; the host's are the first any guest found) and the client is told, which keeps them too. A session writes no file and logs nothing: whoever holds it (S4) shows the parting and saves each side's `replay` for the tools of `core/sim` (the desync report, `tools/platform_hashes.py`). The spike does not make the machines agree again.
7. **A link that closes:** a guest gone (and everything it sent used), each of its seats leaves when its own frame is next built, so the LEAVE is in that seat's frame of the tick its device left in, as a pad pulled out would; the others play on (`NetPlay` lets a gone guest go between ticks before that, which records each leave at the next tick's start just the same). The host gone, the client's replay is closed and ends once played out. **A machine that went silent** (closed, crashed, off the network: no goodbye, and the wire keeps the link open) is taken for gone the same way: once something was heard from it, ten seconds of a session's own stepping with nothing read close the link (`NetSession.SILENT_MS`; both sides send steadily, the client its pings and frames, the host its pongs and ticks). Nothing is counted before the first message (the other machine may still load), and a stall of this machine's own counts a quarter second at most.

Whoever holds a session calls **`after_tick()` after every tick has stepped** (the tests' harness does; in the game `NetPlay`, on the Tick's `ticked`).

## Contract

- **Untrusted bytes.** Every message is decoded strictly before anything is used: the envelope by `NetMessage` (the kind, the length, the kind's own limit, names as plain text, nothing left over), a header and a tick by `Replay`'s decoder, a frame by `InputFrame`'s. No `bytes_to_var`, and no code, resource, path or URL ever comes from the wire. A frame's commands are `InputFrame.COMMAND_NAMES`, as a replay's are.
- **Each side takes only the other's kinds.** The host takes FRAME, HASHES, PING, SEAT_ASK and RUN from each guest; the client HEADER (the first starts its run; each one after is the host's next recording), TICK (in order, of the newest recording it was sent), PARTED, PONG and LOBBY. Anything else, or anything malformed, closes the link, and the session says why (`problem`).
- **Refused is final.** Once a session closed the link for a reason, it reads nothing more from it and uses nothing of it that still waited (the host drops that guest's queued frames and commands, and its seats leave). A guest refused never touches another guest's link or seats.
- **A client plays only its own seats.** A frame names its seat; one for a seat the host did not give that client closes the link (one for a seat it gave back within the last 600 ticks is dropped: it was on its way). A JOIN in a frame seats nobody; only an ask does, and only on a seat nobody holds. A LOBBY names only players 0 to 3, each on one seat. A device is never named on the wire.
- **Limits, each guest on its own.** The host reads at most 64 messages a tick from a guest; holds at most 600 of its frames waiting (all its seats together), each for a tick no earlier than the one before it of that seat and no more than 600 ahead; holds at most 64 commands a seat that wait for a tick's frame with room; writes no tick's frame past a frame's own limits (16 commands, 16 kB: the rest wait a tick); and takes one check per window, in order, of a tick it has played. A check names at most 2,048 areas. The client reads at most 600 messages a step. A loopback end with 8,192 unread messages closes. A guest that joined a run under way is sent at most 240 ticks a tick, and at most 16 of its asks for a seat wait for the tick's end.
- **A link is handed over open,** and carries a whole message of any size up to `NetMessage.MAX_BYTES` (a link whose wire takes less splits and joins it itself: `NetRtcLink`, 16 kB a packet).
- **A pasted code is untrusted text.** `NetCode.read` checks its length, prefix and alphabet, the form of every line it unpacks to, that the description holds the lines a data channel's always does, and each candidate's whole grammar (its address an IP address written out or a browser's `.local` name: nothing a code says is looked up) before WebRTC is handed any of it; a refused code changes nothing and keeps nothing. A handshake takes only the kind of code its side expects (the host an answer, the joining machine an offer). What passes all that may still be refused by WebRTC itself (which logs it): the handshake then fails.
- **What the room server says is untrusted text.** `NetSignal.read` takes only the server's nine forms, written exactly as the server writes them (the keys in their order, no space, nothing more); nothing is parsed as an open object. A handshake takes only its side's kinds, in an order that makes sense (no offer before the room took it, no second room); anything else ends it. A machine's code the server hands over is checked by `NetCode.read` exactly as a pasted one: a refused one costs a host that guest alone. The socket closes on a packet that is not text, is empty, is past 16,384 characters or holds anything but plain printable characters, and on 64 unread messages.
- **The room server is reached only when asked** (a host opening its room, a player joining one by its code), only at `NetSignal.URL`, and a joining machine's socket closes once it is linked. The server sees each machine's address and the codes it carries, and keeps neither (server/signal/README.md).
- **Whom a machine talks to:** the STUN server named in `NetRtc.STUN` (it sees the machine's address, nothing of the game) and the machine whose code was pasted. Nothing listens for strangers, and nothing is made before Host or Join.
- **The WebRTC link's limits:** a packet that is text, empty, too long or marked otherwise, a message past `NetMessage.MAX_BYTES`, 8,192 unread messages or 8 MB of them, or 4 MB waiting to leave close it; a poll takes at most 1,024 packets.
- **A code always holds a candidate:** it is made one poll after the gathering is seen done (the last candidates are handed over by then), and a machine with none after four seconds fails instead of showing a code that reaches nobody. Only the host, once given the answer, runs out of time (thirty seconds); the joining machine waits as long as its player.
- **Files:** only `NetLog` writes one (`user://net/host.log`, `client.log`, the paths written out). A parted run is saved by the frames service (`Frames.save_run`, under `user://replays/`), asked by `NetPlay` with a name of its own, never one from the wire.
- **One recording after another.** A client takes a header after its first as the host's next recording (at most four wait to be played), and plays it once the one before is played out. It tells the host which it plays (RUN: the next one, never one it was not sent; anything else closes the link); the host uses a guest's frames and checks only for the recording it says it plays.
- **A source never seats.** A client's seat is given and taken back by the host session through the input layer (`core/sim/frame_source.gd`): on an ask, on a LEAVE in the seat's frame, and when the client is gone.
- **A run joined a while in is checked from the next whole window:** the host hashed only a part of the window it joined the client in.
- **Sessions read the link only when called:** the host when its seat's frame is built, the client at each physics step's start, and both by `pump()` before the run.
- **The clock is given.** The conditioner and the client's ping run on a clock handed to them (a test's steps; the engine's in the game). Nothing here is simulation state, and the simulation reads nothing here.
