# Tests

## Purpose

Tests for the whole game. The tree mirrors the code: a test for `gameplay/combat/` lives in `tests/gameplay/combat/`. Three special folders hold the checks that run on every build: `smoke/`, `benchmark/` and `bots/`.

## Contract

- Every code change comes with tests. Every bug fix comes with a regression test that would have caught it.
- Tests may depend on any area; no area depends on tests.
- Typed GDScript, like all code, and no banned APIs (AGENTS.md, hard rules).
- Tests never assume a single player: cover more than one player index where it matters.
- Tests are fast and deterministic: no real-time waits, and a fixed seed for any randomness.

## How to write a test: small and isolated

New tests extend `tests/support/suite.gd` (`extends "res://tests/support/suite.gd"`). Every method named `test_*` is one test: it builds what it needs, checks one behaviour with `check(condition, message)` or `check_equal(actual, expected, message)`, and the suite frees whatever was handed to `own(object)`. A failing test is reported by name and never changes the next test. Copy `tests/gameplay/ai/test_ai_telegraph.gd` (a fixture and many short tests) or `tests/core/test_svg_art.gd` (a data-driven check over many files).

- **One behaviour per test**, named for it (`test_a_wizard_who_steps_aside_is_not_hit`). If the name needs "and", split it.
- **Shared setup goes in `before_each` or a fixture file** (a script in `tests/support/` or next to the tests, not named `test_*`), never in leftover state from a test before.
- **Check behaviour, not looks or numbers.** Don't assert a pixel colour, a sprite's exact size, a child's position, a count of decorations or a tuning number (a speed, a damage) unless that is the contract. Check what has to stay true: the shot comes when the telegraph ends, the floor covers the room, a spawn can be reached. Then an art or balance change does not break a test.
- **Look rules are checked once, for every file,** by a data-driven test (`test_svg_art.gd` for SVGs), so a new asset is covered without a new test.
- **Don't test one thing in two places.** If a bigger test already covers it, split the big one instead of adding a copy.
- Every unit test is a suite; only the runners that are not unit tests (`benchmark/`, `smoke/test_four_bot_smoke.gd`, `bots/test_room_balance.gd`) are `SceneTree` scripts of their own.

## How the tests run

`ci/build/unit_tests.sh` runs them, for `ci/build/build.sh --tests` and `tools/ptest.sh` alike, up to one Godot process per core at once, the longest first (by the last run's times, `build/unit-test-times.txt`), each with `--fixed-fps 60`, so a frame is 1/60 s of game time and none waits for the clock (a test counts game time in frames or deltas, never on the clock).

- **Suites run several to a process.** A Godot start compiles nearly the whole game (the autoloads reach most scripts: about 1.5 s on a fast machine, nearly 4 s on a slow one), and it was half of the suite's time when every file had a process of its own. A suite is a node, not a program: the host `tests/support/run.gd` runs the files it is handed one after another, each on a fresh game (every autoload made again, the root's leftovers freed, the tree unpaused, the input map and `user://` reset), and the runner hands it the suites 8 at a time, in batches by path (the same batches on every run of the same tree). Each file still gets its own log and result line. A file that fails in its batch is run again alone: if it passes alone, it still fails, with a note that a file before it left state behind (a static member, a project setting); find what it left and clear it. One test file (or several), by hand: `godot --headless --path . --script res://tests/support/run.gd -- res://tests/<area>/test_<name>.gd`; a runner that is a `SceneTree` script of its own (`benchmark/`, `smoke/`, `bots/test_room_balance.gd`) is `--script res://tests/<area>/<name>.gd`. A test file does not repeat this.
- **A file that needs a process of its own** (one of many seconds, or one that times the machine) says `# unit-test-alone`. A file of many seconds is split: a line `# unit-test-shards: N` in it starts it N times (alone) with `--shard=K/N`, and the suite runs every Nth test method in each (`tests/support/suite.gd`); a long matrix is cut into several methods for it (`test_card_rules.gd`'s modifier parts), and a runner that is not a suite takes the shard itself (`test_stress.gd` by scenario, `test_projectile_timing.gd` by round).
- The suite prints each method's time (`TEST TIME:`), and the runner the five longest files. No test gets a run of its own for its timing: the budgets of the next point hold with other tests beside them.
- **Tests that time the machine** (the owner, 2026-11-20): a budget in wall time is never one reading of `Time.get_ticks_usec` against a fixed number of milliseconds, which a loaded machine breaks (`test_ground_layout.gd` took 155 ms against 150 under `tools/ptest.sh`). It is timed through `support/wall_clock.gd` (its tests `support/test_wall_clock.gd`): `fastest_usec` (the fastest of several runs), or `against`, the work's fastest run in units of a reference workload run in turn with it for as long as it took (`gdscript_reference` for GDScript, `native_reference`, the engine's C++ on one thread, for native work), so a slow or busy machine slows both alike. The budget is the test's usual multiple, measured on a quiet machine and written beside it with the date, times a slack of 1.5, so the code's own 2× slowdown fails on a machine like that one, and a 3.5× oversubscribed one passes (2026-11-20: 8 busy loops and 6 test processes on 4 cores). On another kind of machine a multiple can be some tens of percent off (the interpreter and the engine's C++ are not quicker by the same share everywhere): a usual measured on another machine is moved in the PR, with its numbers. Compare single-threaded work with the single-threaded references: a load takes a threaded run's other cores away, and its speed is the core count's, so a budget runs the native kernels on one thread (the projectile manager's `set_native_threads(1)`, the ground's `threads` 1). The budgets so timed: `core/test_projectiles_kit.gd` (1,500 shots stepped, the kernel on one thread, GDScript references, one usual a path, native or not), `core/test_snapshot.gd` (a restore that lays a biome again) and `gameplay/feel/test_ground_layout.gd` (a fresh layout's lay, for a stall, and every room on one thread, references a megapixel). A test that only reports a time (`test_spell_fuzz.gd`'s slow steps, `test_card_rules.gd`, `test_cover_biome.gd`, `test_snapshot_game.gd`) prints it and fails nothing, and a wait for a real connection (`net/test_net_rtc.gd`'s `PATIENCE_MS`) is a timeout, not a budget. When a change makes the work cheaper or dearer for good, the PR moves the usual multiple, with the numbers it printed.
- **What is slow:** past the start, most of the time is the determinism tests' state hash (`StateWalk`, every tick of every fight, several times a fight): a content fight's 300 ticks step in 0.2 s and hash in about 2 s. A test that hashes should hash only what it compares.

## Allowed files

`.gd`, `.tscn`, `.tres`, `.json` and Godot's `.uid` files, and the sound room's fixture sounds (`sound_room/fixtures/`: `.ogg` and their `.import`, baked by `tools/sound_fixtures.py`). Limit: 1 MB per file.

## Steps

1. Find the area your change is in and use the mirrored path under `tests/` (for example `tests/core/` for `core/`).
2. Write the test as typed GDScript. Cover more than one player index where it matters; use a fixed seed and no real-time waits.
3. For a bug fix, write the regression test first and check that it fails without the fix.
4. Run it (see "Run" below), then run the checks under "Validate".
5. Open a PR using the template.

## Run

```sh
ci/build/build.sh --quick        # downloads the pinned Godot once, imports, runs the editor smoke test
ci/build/build.sh --quick --tests  # the same, then every tests/**/test_*.gd and each card's own content/spells/**/test_<id>.gd
tools/ptest.sh 4 'test_staff'      # after one build: only the test files whose path matches, 4 processes at once
ci/build/build.sh --quick --screenshots  # the same, then every tests/screenshots/shot_*.gd on a virtual display
```

Rules every unit test follows, learned the hard way:

- A suite reads the tree through its own members, as a `SceneTree` script would: `root`, `process_frame`, `physics_frame`, `paused`, `current_scene`, `call_group`; a helper that takes the `SceneTree` is handed `tree`, never `self` (the suite is a node). Its tests run after the root is in the tree. An old test that is a `SceneTree` script of its own (the benchmark and smoke runners) starts `_initialize()` with `await process_frame`: the root joins the scene tree only after `_initialize` returns.
- Leave nothing behind for the next file in the process: free what you add to `root` (`own()` it), stop a run you started, unpause the tree, put back a static member or a project setting you changed.
- The real autoloads exist in the run (`Events`, `Projectiles`, `Combat`, ...). A test of "autoload missing" takes the node out of `root` and puts it back.
- Nodes that the projectile manager must see as targets have to be in the tree.
- The log must have no line starting `ERROR:` or `SCRIPT ERROR:` (the build fails on it); warnings are fine. Free what you create and stop audio players before the end; wait a moment (`await create_timer(0.3).timeout`) so the audio server lets go, or the exit reports leaks and a resource in use.
- Do not `preload` a scene that is also an autoload (like `hud/panels/panels.tscn`): the autoload then fails to load at start. Use `load()` inside the test.
- Compare typed arrays with typed arrays: an `Array[StringName]` never equals an untyped `[&"a"]`.
- Signal handlers must take every argument of the signal.

The Python tests for the CI scripts are in `ci/tests/` and are owner-maintained.

```sh
tools/check.sh

```

## Review questions

Besides the general review (bugs, edge cases, 1–4 players, performance, clarity, fun):

- Does it cover more than one player index where it matters?
- Is it fast and deterministic (no real-time waits, fixed seed)?
- For a bug fix, does it fail without the fix?
