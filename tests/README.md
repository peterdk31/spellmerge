# Tests

## Purpose

Tests for the whole game. The tree mirrors the code: a test for `gameplay/combat/` lives in `tests/gameplay/combat/`. Three special folders hold the checks that run on every build: `smoke/`, `benchmark/` and `bots/`.

## Contract

- Every code change comes with tests. Every bug fix comes with a regression test that would have caught it.
- Tests may depend on any area; no area depends on tests.
- Typed GDScript, like all code, and no banned APIs (AGENTS.md, hard rules).
- Tests never assume a single player: cover more than one player index where it matters.
- Tests are fast and deterministic: no real-time waits, and a fixed seed for any randomness.

## How to write a test: small and isolated

New tests extend `tests/support/suite.gd` (`extends "res://tests/support/suite.gd"`). Every method named `test_*` is one test: it builds what it needs, checks one behaviour with `check(condition, message)` or `check_equal(actual, expected, message)`, and the suite frees whatever was handed to `own(object)`. A failing test is reported by name and never changes the next test. Copy `tests/gameplay/ai/test_ai_telegraph.gd` (a fixture and many short tests) or `tests/core/test_svg_art.gd` (a data-driven check over many files).

- **One behaviour per test**, named for it (`test_a_wizard_who_steps_aside_is_not_hit`). If the name needs "and", split it.
- **Shared setup goes in `before_each` or a fixture file** (a script in `tests/support/` or next to the tests, not named `test_*`), never in leftover state from a test before.
- **Check behaviour, not looks or numbers.** Don't assert a pixel colour, a sprite's exact size, a child's position, a count of decorations or a tuning number (a speed, a damage) unless that is the contract. Check what has to stay true: the shot comes when the telegraph ends, the floor covers the room, a spawn can be reached. Then an art or balance change does not break a test.
- **Look rules are checked once, for every file,** by a data-driven test (`test_svg_art.gd` for SVGs), so a new asset is covered without a new test.
- **Don't test one thing in two places.** If a bigger test already covers it, split the big one instead of adding a copy.
- Old test files (one `_initialize` that runs every check) still work; when you touch one, move the part you touch to the suite (`docs/BACKLOG.md`).

## How the tests run

`ci/build/unit_tests.sh` runs them, for `ci/build/build.sh --tests` and `tools/ptest.sh` alike: every `test_*.gd` under `tests/` and `content/` is a Godot process of its own, up to one per core at once, the longest first (by the last run's times, `build/unit-test-times.txt`), each with `--fixed-fps 60`, so a frame is 1/60 s of game time and none waits for the clock (a test counts game time in frames or deltas, never on the clock). A file of many seconds is split: a line `# unit-test-shards: N` in it starts it N times with `--shard=K/N`, and the suite runs every Nth test method in each (`tests/support/suite.gd`); a long matrix is cut into several methods for it (`test_card_rules.gd`'s modifier parts), and a runner that is not a suite takes the shard itself (`test_stress.gd` by scenario, `test_projectile_timing.gd` by round). The suite prints each method's time (`TEST TIME:`), and the runner the five longest runs. The tests that time the machine (budgets in wall time: `test_projectiles_kit`, `test_spell_fuzz`) run with the rest and only if one fails are run again alone. The whole suite takes about a minute on 24 cores, most of it Godot's start (about 1.2 s a process, alone).

## Folders

- `smoke/`: the boot smoke test (`boot_smoke.gd`), which starts the main scene and fails unless the menu comes up, and the 4-bot smoke test (`four_bot_smoke.gd`): four bots join and play the first room, bot 4 idles in its builder, and it passes only if `room_cleared` arrives, players 1–3 are alive or revived, bot 4's overlay stayed open, and the log has no `push_error`, no `ERROR:` line and no "the restart failed" warning. `error_log.gd` is its error logger (unit test `test_error_log.gd`). The checks live in the node `four_bot_runner.gd`; `four_bot_smoke.gd` (a `SceneTree` script) adds it to the root, and `test_four_bot_smoke.gd` runs that under `build.sh --quick --tests`. An exported binary hangs on `--script` while the autoloads start, so in the `Linux Test` export the main menu adds the same node when the user argument `--four-bot` is given and the file exists: `build/linux-test/Spellmerge.x86_64 --headless -- --four-bot`. A build that fails a smoke test is broken.
- `benchmark/`: the performance checks. `probe.gd` rides along in the 4-bot test and prints `BENCH:` lines (frame time, peak nodes, projectiles, memory, live hit particles); `projectile_timing_runner.gd` times the projectile manager at both caps with four players (`test_projectile_timing.gd` starts it from the command line). Both it and the stress run are also nodes the main menu adds in the Linux Test and Web Test exports on the user argument `--projectile-timing` or `--stress`, like `--four-bot` (`build/linux-test/Spellmerge.x86_64 --headless -- --stress`); in the web export they give the WASM numbers. `stress.gd` is the stress scene (from the command line: `godot --headless --path . --script res://tests/benchmark/stress.gd`; about a minute, longer in the web export): 4 bots with built spells on the real game, 100 enemies and 1,000 shots (web; the web cap, `DEFAULT_CAP_WEB`), then 200 and 6,000 (desktop, `DEFAULT_CAP_DESKTOP`), full effects; between them the web scenario runs again with the render loop off and with hit particles off, and each scenario prints `BENCH: frame parts` (physics steps per frame, physics, process and renderer time) and `BENCH: stress parts` (enemy step, combat lookups, Feel's step) to explain a slow web frame. It prints `BENCH:` lines and `STRESS OK`; `test_stress.gd` runs a short version in the build. They print and gate nothing: over a budget, and for a frame-time regression over 10%, the plan is a warning with likely fixes, never a broken build (docs/PLAN.md, "Gates are sparse"). Headless numbers (not web numbers) are in `docs/LOG.md`. `fire_cap.gd` (with `fire_cap_runner.gd`; a few minutes, not run in the build) sweeps the per-step fire pacing (`Spells.fire_shots_per_step`) over trigger-heavy staffs of the real cards and times what one payload fire costs (a burst of `on hit` shots against the same burst without, paced and not), for tuning that pacing; `fire_cap_view.gd` shows the same burst in a window on the real autoloads, with a graph of the step time (`godot --path . --script res://tests/benchmark/fire_cap_view.gd`; keys 1-3, P, T, Space) (owner, 2026-10-29). `shot_gpu.gd` (not run in the build; it needs a window, a GPU or `xvfb-run` with llvmpipe) renders a fixed scene of shots stepped by hand (60, 400 and 3,000) and prints the GPU time of a frame and the vertices the trail batches send; `-- --frames=DIR` saves the frames, the same on every run of the same code, so two checkouts can be compared pixel by pixel (`--plain` leaves out lightning and dashes, which draw in batches of their own; `--only=few|some|many` runs one scenario and `--timed=N` times N frames, for quicker comparisons; llvmpipe's times vary by 10% or more from run to run, so compare several runs taken in turn) (performance, 2026-11-02). `sandbox_storm.gd` (with `sandbox_storm_runner.gd`; not run in the build, about 15 seconds) is the bullet showcase: one wizard in the real sandbox stands among the training dummies and holds the `dev` staff's split nova build (Y, `Flow.SANDBOX_START_CARDS`), and it prints the shots made and alive against the cap and the hits and damage on each dummy (`BENCH: storm`, `STORM OK`); in a window (`godot --path . --script res://tests/benchmark/sandbox_storm.gd -- --stay`) a line at the bottom shows the live counts and it keeps casting; `--seconds=N`, `--cap=N`, `--no-native` and `--cards=a,b,c` (another build on the storm's staff, card ids: a beam build, whose hits are not shots, passes with none) change the run. The main menu also adds its runner in the Linux Test and Web Test exports on `--storm`, so the storm runs on a real GPU in a browser: the Web Test export in Chrome without vsync, the page's `args` read like user arguments, its frame time the real one (the owner's measure for performance, 2026-11-04; the windowed d3d12 run under WSLg was too slow). `combat_hit.gd` (not run in the build; a few seconds) times Combat's own work for a spell's hit, `_on_projectile_hit` called directly with nothing else listening: a plain bolt, and frost, fire and storm bolts on a body frozen, burning or hexed, the fastest of 15 passes in microseconds a hit (`BENCH: combat hit`; the hit's listeners are timed by `sandbox_storm.gd -- --profile-signals`) (performance, 2026-11-02). `ai_step.gd` (not run in the build; a few seconds) times the enemy AI: 200 staffed strays of every kind, each on its own profile, round four wizards that walk and cast, and prints the median and p95 of one `Actor.step` pass over the crowd (enemy AI L1, docs/milestones/M2-enemy-ai.md). `prop_cost.gd` (with `prop_cost_runner.gd`; not run in the build, under a minute) is what a prop costs the simulation (props W1, docs/milestones/props.md): it stands 0, 300 and 1,000 stand-ins (`prop_stand_in.tscn` and `.tres`: an actor with Health, a Hurtbox and a Caster of two staffs, no controller, no Mover) in the real hub, runs the Tick itself and prints, for each count, the tick's time (and its steps one by one, and each part of a stand-in's step), the state hash whole and spread over 60 ticks, and a snapshot taken and restored with its bodies matched and made again (`BENCH: props`, `PROP COST OK`); `--counts=0,300,1000` changes the counts. `shot_scale.gd` (not run in the build; a few minutes headless) is shot scale's baseline (H0, docs/milestones/shot-scale.md): a storm (shots over a large arena past eight bodies), a crowd (the same shots among 500 moving bodies, with the game's hit-work budget) and `crowd_all` (the crowd with the budget lifted, every shot tested every step) at 10,000, 30,000, 50,000 and 100,000 live shots of a real spell, on the real Spells, Combat and Feel stepped by hand, with the game's tails (motes; `--tails` for the tail shader's). The projectile manager times its own `step()` in its passes (`step_profile`, core/README.md): the hit pass split into the kernel's time and the hand-backs with their listeners, the hand-backs, hits and shots past the hit budget a step; then the other areas' steps, `update_draw` and, in a window, the GPU's frame; a second pass times each hit event's listeners (`BENCH: shot scale listener`). It prints each scene's hits and damage (`HITS:`, `DAMAGE:`) for the damage check; `--counts=`, `--only=storm,crowd,crowd_all`, `--steps=`, `--crowd=`, `--cards=`, `--work=`, `--tails`, `--no-native` and `--no-listeners` change the run.
- `build.json`: the build settings: the size and load-time budgets (they only warn), and which of these runs `ci/build/build.sh` starts in the `Linux Test` and `Web Test` exports: per run its user argument, the line its log must have on Linux and on the web, the web timeout, and whether its result lines go into the Daily log (`bench`); `ready` is the line the main menu prints. Add a run here when the main menu starts a new runner on an argument; only Claude's PRs may change the file, and the hard rules refuse a value `smbot.config.parse_build` can't read.
- `bots/`: the bots that play headless runs for smoke tests and playtest reports. `bot.gd` plays one slot: it joins with a virtual device and fills its seat's input frames (a `FrameSource`, `Frames.set_source`; online-ready N2), as a device's local input layer does, so the game cannot tell it from a person: a fighter decides by the enemies' own AI (enemy AI L5, docs/milestones/M2-enemy-ai.md): it owns an `AIBrain` driving its wizard with the bot profile (`bot_profile.tres`: no rest, `press_on` 1, quick to react, dodging, no randomness), the brain fills a spare `ActorIntent` at each tick's start (when the frames service asks, `fill_frame`) and the bot turns it into its frame (the walk each axis on or off as the move keys, the aim, a press per pressed staff, the button held per held staff; `send`). On the players' team the brain winds up nothing, so it casts the step a staff is ready; it plays all four staffs by what each casts next (`CastSense`, never a card id), walks round walls (`AISight`), dodges shots and telegraphs aimed at it, and dashes with whichever staff's next cast moves the caster (no button is "the dash"); an idler only taps `back` (B, its builder). A bot reads no spell field; the player calls the spell's one cast method. A bot can also build (`build_random(seed)`: a seeded random staff from `staff_fuzzer.gd`, sent slot by slot as `staff_change_requested` into staff 3) and open its builder (`open_builder()`, one press of B). `test_spell_fuzz.gd` compiles and casts 300 seeded random staffs (`staff_fuzzer.gd`) in the combo arena and fails on an error line, a cycle that runs away or a staff that never casts; shots dropped at the pool and slow steps are reported (with the costliest staffs), not failed, since there are no build limits.
- `screenshots/`: scripts named `shot_*.gd` that set up a scene and save 640×360 PNGs (and crops of them) to `user://screenshots/`. Each extends `tests/support/screenshot.gd` and stages its shots in `take()`, with the base's helpers (`need`, `settle`, `shot`, `snap`, `save_crop`, `tap`, `lay_floor`, `place`, `label`); before `take()` the base compiles the shaders as Play does (`support/warm_up.gd`: Flow's play tasks through `Loading`), so every shot is taken after the game's own start (a script that shows the load itself, `shot_loading.gd`, sets `warm_first = false` in `_init()`; the clip recorder warms up the same way); it is not a test and only fails when a staged state did not happen. The build copies the PNGs to `build/screenshots/`; they are posted on every bot PR and on the site's `/screenshots/` page by the daily build. The build runs up to 8 at once, each on its own `xvfb-run` display (or on `$DISPLAY` when `xvfb-run` is missing) and with `--fixed-fps 60`, so a frame is always 1/60 s of game time however busy the machine is: a script waits in frames or with `wait_for`, never on the clock. One script: `SHOTS_ONLY="shot_cards" ci/build/build.sh --quick --screenshots`, or `godot --path . --fixed-fps 60 --script res://tests/screenshots/shot_<name>.gd` on a display. `shot_cards.gd` finds every card through the registry, so a new card shows up on `cards_sheet` with no edit (the sheet goes on to `cards_sheet_2` and on when the cards fill a screen).
- `clips/`: the clip recorder (#245). `record.gd` casts one scripted scenario per clip on a stage (`stage.gd`: the real spell runtime, projectile manager, combat and Feel, fresh for each clip, stepped by hand 1/60 s at a time) and saves a frame sequence to `user://clips/<id>/`: `meta.json` (`{"id", "kind", "title", "fps"}`, fps 20) and `frame_0000.png` and up, 320×180 game pixels around the middle of the action, at most 240 frames and 3.5 MB per clip (the format is read by `ci/smbot/clips.py`). `ci/build/build.sh --quick --clips` runs it under `xvfb-run` (a headless run has no pixels), copies the folders to `build/clips/` and the pipeline turns them into animated PNGs. Clips are build output and are never committed. The user arguments are the ids to record (none means all; `--list` prints them): `CLIPS_ONLY="combo_shatter reaction_thaw" ci/build/build.sh --quick --clips`. `scenarios.gd` reads the scenarios from the content, so a new row or component is a clip with no code change:
  - `combo_<id>`: every combo file (each in its card's `combos/` folder), cast as the row says (`casts` as card rows, `imps`, `seconds`), the same scripted cast as `test_combos.gd`.
  - `form_<id>`, `element_<id>`, `modifier_<id>`, `trigger_<id>`: one per component in the registry, alone (a bolt for an element or a modifier, a bolt that holds a nova of bolts for a trigger), against three imps.
  - `reaction_<id>`: one per reaction in `reactions.tres`: a bolt of the element that gives the status, then 0.3 s later a bolt of the row's element. `reaction_<id>_coop`: the same with two players standing apart, one bolt each.

  `test_clip_scenarios.gd` (headless) checks the scenarios, that every reaction clip sets its reaction off and that a stage played twice gives the same simulation; the frames themselves need a display. Two takes of a clip are identical frame for frame, because Feel's hit sprays (CPU particles, which follow real frame time) are left out; to check, run the recorder twice and `diff -rq` the two `build/clips` folders (docs/DECISIONS.md, 2026-10-25).
- `platforms/`: the same game on every platform (online-ready N2b, docs/milestones/online-ready.md). `replay_hashes_runner.gd` records and plays back a scripted sandbox fight and a wave of two bots (`tests/support/replay_run.gd`) at a fixed seed and the web's shot cap, and prints every tick's state hash per area (`REPLAY TICK`), the kept tick's leaves (`--keep=SCENE:TICK`) and `REPLAY HASHES OK`. The daily run plays both scenes in the full build's three test exports, each on its own runner (`.github/workflows/platforms.yml`, N8).
- `net/`: online play (the netcode spike S2, `net/README.md`): the messages and their decoder with a fuzz, the loopback and the conditioner, each session against a hand-written peer, and `net_pair.gd`, two scripted fights (`tests/core/content_fight.gd`) linked by the sessions over a conditioned loopback on a clock of physics steps, which `test_net_session.gd` plays at round trips of 0 to 200 ms with jitter and loss (the same state at every tick, the host on time, a stall caught up, a disturbed world caught by the checks, the received replay played offline). S4: `test_net_code.gd` (the codes two players swap, with a fuzz), `test_net_rtc.gd` (two WebRTC peers in the test process swap codes and link with no STUN server; messages whole and in order both ways, the large ones split; two scripted fights through the real link agree at every tick; needs the extension), `test_net_play.gd` (Host and Join, the autoload `NetPlay`, on two machines with the stand-in handshake `loop_handshake.gd`: the phases, the seats, refused codes, loading before the run, either machine leaving, a failed check said and saved), and `online_runner.gd` (not a unit test: the real game in two processes, started by `tools/online_pair.sh` through the main menu's `--online`). `benchmark/net_grid.gd` (not run in the build; about half a minute) runs the same pair over the grid of round trips and losses and prints each run's counters (`BENCH: net grid`: the input delay, a press's time to its tick, late frames, waits, bytes a second, link and hash time a tick; `--ticks=N`, `--card=ID`, `--delay=D`, `--guests=N`). - `support/`: the suite base class (`suite.gd`) and the screenshot base class (`screenshot.gd`) and the warm-up the screenshots and clips start with (`warm_up.gd`). Fixtures shared by several tests live here (`staff_kit.gd` for old recipe shapes as card rows; `fake_cards.gd`, any number of made-up cards behind a stand-in registry, for the radial builder's tests and screenshots; `fresh_game.gd`, every autoload made again in the project's order, for a test that compares two runs from the same start; `replay_run.gd`, a run on the real game recorded through the Frames autoload and played back from a fresh game, each tick's state hashes captured, shared by `tests/core/test_replay_game.gd` and the platform runner). ## Allowed files

`.gd`, `.tscn`, `.tres`, `.json` and Godot's `.uid` files. Limit: 1 MB per file.

## Steps

1. Find the area your change is in and use the mirrored path under `tests/` (for example `tests/core/` for `core/`).
2. Write the test as typed GDScript. Cover more than one player index where it matters; use a fixed seed and no real-time waits.
3. For a bug fix, write the regression test first and check that it fails without the fix.
4. Run it (see "Run" below), then run the checks under "Validate".
5. Open a PR using the template.

## Example to copy

`tests/smoke/boot_smoke.gd`, the boot smoke test. Copy its structure for a new test.

## Run

```sh
ci/build/build.sh --quick        # downloads the pinned Godot once, imports, runs the editor smoke test
ci/build/build.sh --quick --tests  # the same, then every tests/**/test_*.gd and each card's own content/spells/**/test_<id>.gd (about a second each)
ci/build/build.sh --quick --screenshots  # the same, then every tests/screenshots/shot_*.gd on a virtual display
```

Rules every unit test script (a `SceneTree` script) follows, learned the hard way:

- Start `_initialize()` with `await process_frame`. The root joins the scene tree only after `_initialize` returns, so before that nodes added to `root` are not in the tree (no `_ready`, no `global_position`, no absolute `get_node` paths).
- The real autoloads exist in the run (`Events`, `Projectiles`, `Combat`, ...). A test of "autoload missing" takes the node out of `root` and puts it back.
- Nodes that the projectile manager must see as targets have to be in the tree.
- The log must have no line starting `ERROR:` or `SCRIPT ERROR:` (the build fails on it); warnings are fine. Free what you create and stop audio players before the end; wait a moment (`await create_timer(0.3).timeout`) so the audio server lets go, or the exit reports leaks and a resource in use.
- Do not `preload` a scene that is also an autoload (like `hud/panels/panels.tscn`): the autoload then fails to load at start. Use `load()` inside the test.
- Compare typed arrays with typed arrays: an `Array[StringName]` never equals an untyped `[&"a"]`.
- Signal handlers must take every argument of the signal.

The Python tests for the CI scripts are in `ci/tests/` and are owner-maintained.

## Validate

```sh
tools/check.sh
ci/build/build.sh --quick
```

## Review questions

Besides the general review (bugs, edge cases, 1–4 players, performance, clarity, fun):

- Does it cover more than one player index where it matters?
- Is it fast and deterministic (no real-time waits, fixed seed)?
- For a bug fix, does it fail without the fix?
