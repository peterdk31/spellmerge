# Tools

## Purpose

Scripts that contributors and Claude run on their own checkout. `tools/check.sh` runs the same hard rules as the `rules` check in CI on your changes, so you can fix problems before you open a PR. `tools/atlas.py <out>` writes the Spell atlas data (`atlas.json`: one entry per component, combo and reaction, read from `content/`; `build.sh --clips` calls it, and `ci/smbot/clips.py` has the format); its tests are `tools/test_atlas.py` (`python3 -m unittest discover -s tools`). `tools/staff_art.py` draws the curl staff at 2x detail (ART0, the pilot of the 64x64 redraw; art/README.md, "Redrawing a sprite at 64x64"): its head sheet (16 drawn directions by 4 ramps, 96x96 frames), the Optimist's eye and brow sheets (32x16 frames) and the golden example `art/kit/golden_staff@2x.svg`, from shape rules (rects only, palette colours, read from docs/STYLE.md); `--check` writes nothing and fails when an SVG differs from what the rules draw; its tests are `tools/test_staff_art.py`. `tools/pixel_grid.py <name>.grid.json...` draws pixel art from a grid of characters (props W7, docs/milestones/props.md): a grid file, kept beside its art, names a palette colour for each character (docs/STYLE.md's palette, read from there) and the mote-point characters (`*` by default), and it writes `<name>.svg` (rects only, one a run of a colour along a row, as tests/core/test_svg_art.gd wants) and, when the grid has mote points, `<name>_motes.svg` (the points alone, a mask for a prop's look to give off motes from), so a prop's art and where its motes come from are one source; `--check` writes nothing and fails when an SVG differs from its grid. Its tests are `tools/test_pixel_grid.py`, which also checks every grid in the repository against its SVGs. `tools/ptest.sh [jobs] [path-regex]` runs the Godot unit tests in parallel (one import, a user folder per test), about a minute for the whole suite; it needs the pinned Godot that `ci/build/build.sh --quick` downloads. It prints each failed file with the lines of its log that say why (`tools/ptest_failures.py`: the runner's note on a file that failed only in its batch, with a crash's or a timeout's exit code, the failed checks and the engine's errors), since a cloud session's logs go with its machine; its tests are `tools/test_ptest_failures.py`. `tools/platform_hashes.py run` is online-ready's first look across platforms (N2b, docs/milestones/online-ready.md): it exports Linux Test, Windows Test and Web Test into `build/`, plays the same recorded runs in each (`--replay-hashes`, tests/platforms/replay_hashes_runner.gd: Linux headless, Windows through WSL's interop, the web in headless Chromium through `smbot.websmoke`) and names the first tick, area and members where a platform parts from Linux; `play NAME --build DIR` plays one export already built (`linux`, `linux-gdscript`, `windows` or `web`; the daily run's `platforms` job plays each on its own runner, Windows on a Windows runner) and `compare LOG...` compares saved logs with the first, giving each parting area's two hashes. A run also says what its export was built with (`REPLAY BUILD`): an export whose WebRTC extension is missing or did not load is reported on its own, apart from the hashes (the one check of the Windows build's; `run` sets the extension up with `ci/build/webrtc.sh` before it exports). It writes only under `build/` (and a copy of the Windows export under %TEMP%), needs one `build.sh --quick` and, for Windows, WSL; its tests are `tools/test_platform_hashes.py`. `tools/online_pair.sh [ticks]` plays the real game twice on this machine (netcode spike S4): two headless processes go through Host and Join over WebRTC with no STUN server, their codes handed over as files under a `user://` of their own (`build/logs/online/`), play the hub with both seats scripted (`tests/net/online_runner.gd`), and it passes when every hash check agreed; about fifteen seconds for the default 600 ticks. `tools/online_signal.sh` runs the room server's own tests (`node --test` in `server/signal/`), then starts the server on this machine (`local.js`, Node alone) and plays the game's real handshake through it; `tools/online_room.sh [ticks]` plays the real game twice through a room on that server (online lobby L2: Play, the altar, the code, two players a machine, the stone, a run) and passes when every hash check agreed. `tools/online_party.sh [ticks]` does the same with four processes, a host and three guest machines of one player each (L3). All three need Node 22 or later. `tools/ground_shape.py <shape file>...` draws a room's ground from its shape file (hub rework HR2, docs/milestones/hub-rework.md; content/rooms/README.md, "A room's ground from a shape"): the room's `<room>_ground.tscn` beside the shape and its art in `art/grounds/<room>/`, from the shape's outlines or frame, pits, cracks and areas (a material's colours drawn by `ground_materials.py`, a wall's top and face by `ground_walls.py`, both used only by it; crypt rework CR2, docs/milestones/crypt-rework.md), its edge style (content/edges) and ground materials (content/grounds), the same files every time; `--check` writes nothing and fails when a room's ground is older than what it is drawn from. Standard library only (it writes its PNGs itself); about ten seconds for the hub. Its tests are `tools/test_ground_shape.py`, which also checks every shape file's ground is up to date (drawing every room again, in parallel, a process a core: about 30 seconds on 4 cores; keep the generator's hot loops cheap, as the CI job that runs these tests has 5 minutes). **The game draws the same ground** as a room is laid out (connected biomes CB4): `gameplay/feel/ground/` is this generator's drawing in GDScript, line by line, and `native/src/ground_kernel.cpp` its native twin, so a change to `ground_shape.py`, `ground_materials.py` or `ground_walls.py` is made in both in the same PR (a speed-up that draws the very same bytes, such as the Python's caches, need not be); `tests/gameplay/feel/test_ground_drawing.gd` fails while the game's drawing of a room is not its baked art to the pixel. A length is `length_of` (the square root of the sum of the squares), never `math.hypot` or `math.dist`, which round otherwise now and then.

**The sound tools** (sound plan AU2, docs/milestones/sound.md): `tools/sound.py bake [recipe or id ...]` bakes sound recipes into `.ogg` files (every recipe when none is named). A recipe is `<id>.sound.json` in a folder of its own named `<id>` (`audio/sfx/<id>/`, or a content item's `sounds/<id>/`), and names shared instruments in `audio/patches/<name>.patch.json`. The synth, `sound_synth.py` (sources, envelopes, filters, drive, crush, reverb; standard library only), renders each variant; the bake places its loudness on its family's target and checks its true peak and its top (how loud its part above 2 kHz is, against the family's ceiling, or the recipe's own `top`) (`sound_meter.py`, BS.1770; the families' numbers are read from docs/STYLE.md, "Sound"), then writes in the recipe's folder only: `variants/1.ogg` ... and `<id>.tres` (an `AudioStreamRandomizer` with the family's jitter) for a one-shot, or `<id>.ogg` and its `.import` with `loop=true` for a held loop, and the folder's `assets.json` (an entry a file, with the recipe's hash, loudness and peak). A file whose audio is the same (its 16-bit samples' hash, `audio_hash`, so another encoder rewrites nothing) is not rewritten, and an existing `.import` never is; changing a sound's kind removes the files of its old kind; Godot's import (the pinned Godot, or `$GODOT`) then completes the new `.import` files. `tools/sound.py sheet <recipes, ids or a family> --out DIR` writes a contact sheet outside the repository (`sheet.ogg`, and `sheet.mp4` with the same audio over a card of the ids, for a PR): each sound's variants in turn, four of it at once, then all of them together. `tools/sound.py check` reads no audio: every recipe validates, every file it makes is there with a current `recipe_hash`, and no `.ogg` lacks a recipe unless its manifest entry is `origin: human` (`UNRECIPED`, the list of files made before the tool, is empty since AU6 remade the ambience, and stays so). **Music** is a score, `<track>.score.json` in a folder of its own under `audio/` (`audio/music/<track>/`): `sound_score.py`, the sequencer, renders its layers (instruments from the patches, one-bar patterns of notes, chords `D3+F3+A3`, hits `x`, rests `.` and holds `-`), each exactly `bars × beats × 60 / tempo` seconds and seamless round its end; the bake places all of a track's layers by one scale on the music target and writes `<layer id>.ogg` a layer (with a `loop=true` `.import`) and the folder's `assets.json`; `bake`, `sheet` and `check` take scores as recipes (by path, track or layer id, or `music`), and the sheet plays a track's intensities in turn. Its tests: `test_sound_score.py` (the validator, one length, the seam, the placing, the bake and a fingerprint of the sequencer's sound: `VERSION` in `sound_score.py` is raised as `GENERATOR` is). Its other tests: `test_sound_synth.py` (the three samples the owner chose, as recipes, and the validator), `test_sound_meter.py` (reference tones), `test_sound_bake.py` (the bake, manifest and sheet), `test_sound_golden.py` (a fingerprint a source and shaper: a change to the synth's sound fails it until `GENERATOR` is raised) and `test_sound_hashes.py` (the check, on the repository); about 25 seconds in all.

**The sound room's fixtures** (sound plan AU4): `tools/sound_fixtures.py bake` bakes the sound room's fixture sounds into `tests/sound_room/fixtures/<id>/` with the sound tool's own bake (AU2's three samples and held loop, `SAMPLES` and `HELD` in `test_sound_synth.py`, and a two-layer track, `TRACK` in it), each folder's `assets.json` naming its recipe there; `check` (run by `test_sound_fixtures.py`, with the layers' one length) names a fixture baked from an older recipe. They are outside `sound.py check`'s scan (audio/ and content/).

**Editor scripts** (`@tool`, allowed here and in core/ only, by the owner's decision of 2026-11-11; AGENTS.md, hard rule 4): `cover_preview.gd` (`CoverPreview`, ground cover GC3, a `RoomPreview` of core/base) draws a room's whole ground cover in its scene as the game will lay it (`CoverSketch`, core/base), looking at the room again twice a second, and is taken out before play (content/rooms/README.md, "Decoration"); `prop_stand_in.gd` (`PropStandIn`), `enemy_stand_in.gd` (`EnemyStandIn`) and `item_stand_in.gd` (`ItemStandIn`, items I6: a premade staff of content/items/ or a card, drawn as its head or icon) place a prop, an enemy or an item in a room's scene and show it in the editor as the game will (content/rooms/README.md, props W8b). They never run in play: Flow takes them out of the room and reads only their `prop`, `enemy` or `item` (an item lies on the ground, the Items area's, gameplay/items/). `socket_preview.gd` (`SocketPreview`, connected biomes CB2, a `RoomPreview`) draws a template's sockets (`RoomSocket`, core/base) as a biome will join them: each mouth, its landing and the cut a biome opens to the template's edge, an arrow out of the slab, red where a socket breaks `PieceShape`'s rules, over the 32 px grid, optionally as the template is mirrored; it looks at the room again twice a second and is taken out before play.

**Not an area for content PRs.** Scripts here run on contributors' machines, so they change only through Claude's PRs or the owner's.

## Contract

- Tools only read the repository and report, or write the files they are asked for (`atlas.py` its out file, `pixel_grid.py` a grid's SVGs); they never change anything else, push or open PRs (`ground_shape.py` the ground scene and art of the shapes it is named; `sound.py bake` the files in each recipe's own folder, then Godot's import, which writes the `.import` of any file in the project not yet imported; `sheet` only outside the repository).
- They depend on git and Python 3.10 or newer, nothing else (`ptest.sh` also needs bash and the pinned Godot); `sound.py bake` and `sheet` also need ffmpeg with libvorbis, and the sheet's video libx264 and aac. a bake without ffmpeg stops and says what to install, and `sound.py check` and every test need only Python). Pipeline Python code lives in `ci/smbot/`, which is owner-only; `check.sh` is a thin wrapper around it. `atlas.py` is self-contained (standard library only) because it reads the game's content, not the pipeline.
- They work in any clone with an `origin` remote, and still run (on the local copy) when they can't fetch.

## Allowed files

`.sh` and `.py` scripts and the editor scripts (`.gd`, with their `.uid` files) (Claude's PRs only) and this README. No binaries, archives or downloaded tools.

## Steps

Run the check from the repository root before every PR:

```sh
tools/check.sh
```

It fetches `origin/main`, then checks everything you changed against it: committed, uncommitted and new files. It runs `python3 -m smbot.rules --base origin/main --worktree`, and any flags you add are passed on:

- `--author LOGIN`: the PR author's GitHub login, which decides the path rules. The default is an outside contributor. `--author 'spellmerge-bot[bot]'` applies Claude's wider rules (docs, plan files, `tools/` scripts).
- `--format text|github|json`: `text` (the default) for people, `github` for CI annotations, `json` for scripts and agents.

Every problem is printed as the rule, the file and line, what is wrong and how to fix it. The script exits with 1 when there is an error, and with 0 when there are only warnings or nothing. Empty placeholder files that an agent's sandbox leaves in the working directory (`.bashrc`, `.gitconfig`, `.idea/` and similar) are skipped.

## Example to copy

`tools/check.sh`: a short POSIX `sh` script that changes to the repository root, fetches `origin/main` and runs the Python module with `PYTHONPATH=ci`.

## Validate

```sh
tools/check.sh                              # your change, as an outside contributor
tools/check.sh --author 'spellmerge-bot[bot]'  # Claude's own PRs
PYTHONPATH=ci python3 -m unittest discover -s ci/tests -t ci   # the rules' own tests
```

## Rating questions

Besides the standard criteria (fit, quality, value, risk, scope):

- Does it only read and report, with no side effects on the checkout or GitHub?
- Does it run with just git and Python 3.10+ (and ffmpeg, only to bake sound), and keep working offline?
- Does it give the same answer as the `rules` check in CI?
